## Why

診斷面板告訴使用者「手機請連（預設路由位址）：http://172.20.10.7:8080」，而使用者用手機開這個網址連不上。

實測釘出了成因，而且不在這個系統裡：

| 檢查項 | 結果 |
| ------ | ---- |
| 伺服器監聽位址 | `*:8080`（所有介面，不是只有 127.0.0.1） |
| macOS 應用程式防火牆 | 已關閉 |
| 從 Mac 自己連該位址 | HTTP 200 |
| 預設路由閘道 | `172.20.10.1` |
| 該網段上的成員 | 只有閘道與這台 Mac 兩個 |
| 另一個網路介面 | 只有 link-local 位址，無法使用 |

`172.20.10.0/28` 是 Apple 個人熱點固定使用的網段。這台 Mac 是熱點的**用戶端**，而閘道 `172.20.10.1` 就是提供熱點的那支 iPhone —— 使用者確認過，那正是他用來開網頁的同一支手機。熱點的設計是「用戶端連往網際網路」，主機不路由到自己的用戶端，所以這個位址在那支手機上必然打不開。

位址是對的，伺服器是對的，這個拓撲裡沒有任何可用的位址。但診斷仍然給了一句**必然失敗的指示**，而且沒有任何提示。這與這個端點的既有模式相矛盾：四個探測階段每一個失敗都會附上一則後續動作，那正是它存在的理由；位址這一行卻沒有。

## What Changes

- 當回報的位址落在 `172.20.10.0/28` 時，診斷回應為位址欄位附帶一則警示與一則後續動作；前端在位址那一行之後呈現它們。
- 警示文字只陳述網段事實、不斷言網路拓撲：寫「這個位址屬於 iPhone 個人熱點的網段」而不是「你正在使用個人熱點」。後續動作為「讓 Mac 與手機一起連到一般的 Wi-Fi 路由器」。
- 位址本身照舊回報，不隱藏也不改寫。
- 位址不在該網段時，回應與畫面與現況完全相同。

## Non-Goals

- **不列舉所有網路介面。** 在這個拓撲下列舉找不到任何可用位址 —— 唯一的另一個介面只有 link-local 位址。既有規格也明文記錄了「只回報預設路由位址、不列舉」的決定與理由。真正缺的不是更多位址，是一句「為什麼這個位址在你手機上打不開」。
- **不讀取預設閘道來提高判定精度。** 讀閘道要另外執行系統指令，而位址在手上就有。誤判的風險由措辭承擔：只陳述網段這個事實，即使某台路由器剛好用同一個網段，那句話仍然為真，判斷留給使用者。
- **不嘗試自動修正網路。** 切換 Wi-Fi、關閉熱點都是使用者在系統設定裡的操作，這個系統不碰。
- **不改變位址欄位本身的格式或取得方式。** 取得位址的既有做法（以 UDP socket 讓作業系統挑出對外介面）不變。
- **不改變四個探測階段的輸出與三態語意。**

### Modified Capabilities

- `connection-diagnostics`: 伺服器位址的需求目前只要求「標示為預設路由位址而非唯一位址」。新增規定：位址落在個人熱點網段時，回應須附帶警示與後續動作，且警示須陳述網段事實而非斷言拓撲；位址本身仍照舊回報。

- `project-documentation`: 功能涵蓋表新增本次功能與其錨點詞，以滿足「新增功能時須於同一個變更中加入涵蓋表」的既有需求。
