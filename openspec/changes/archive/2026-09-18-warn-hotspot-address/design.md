## Context

診斷端點回報一組伺服器位址，供使用者在手機上開啟控制介面。位址由一個既有函式取得：開一個 UDP socket 連向外部目標，讓作業系統挑出對外介面後讀回本端位址。它只回報預設路由那一個位址，既有規格明文記錄了「不列舉所有介面」的決定。

實測這台機器的結果：預設路由閘道為 `172.20.10.1`、Mac 位址為 `172.20.10.7`、伺服器監聽 `*:8080`、應用程式防火牆已關閉、從 Mac 自己連該位址得到 HTTP 200、該網段上只有閘道與這台 Mac 兩個成員、另一個網路介面只有 link-local 位址。

`172.20.10.0/28` 是 Apple 個人熱點固定使用的網段（閘道 `.1`，遮罩 255.255.255.240）。因此這台 Mac 是熱點的用戶端，而閘道就是提供熱點的那支 iPhone —— 也正是使用者用來開網頁的同一支。熱點主機不路由到自己的用戶端，所以該位址在那支手機上必然打不開。

診斷面板的四個探測階段各自帶有顯示名稱、結果、細節與失敗時的後續動作，前端以既有的樣式類別分別呈現細節與後續動作（後者帶「→」前綴）。位址那一行沒有對應的細節與後續動作欄位。

## Goals / Non-Goals

**Goals:**

- 使用者在手機上打不開那個位址時，畫面上就說得出為什麼，以及下一步該做什麼。
- 不在其他網路環境下改變任何既有輸出。

**Non-Goals:**

- 不列舉所有網路介面。
- 不讀取預設閘道來提高判定精度。
- 不嘗試自動修正網路設定。
- 不改變位址的取得方式或格式。
- 不改變四個探測階段的輸出與三態語意。
- 不新增或修改任何 CSS 規則。

## Decisions

### 只比對位址前綴，不讀取預設閘道

判定依據是回報的位址是否落在 `172.20.10.0/28`。這個資訊手上就有，不需要額外執行系統指令或解析其輸出。

考慮過的替代方案：另外讀取預設閘道，確認它等於 `172.20.10.1` 之後才提示。否決 —— 它需要執行外部指令並解析輸出，那是一個會隨作業系統版本改變的介面；而它換來的精度，由措辭本身就能取代（見下一項決策）。

### 警示只陳述網段事實，不斷言網路拓撲

文字寫「這個位址屬於 iPhone 個人熱點的網段」，不寫「你正在使用個人熱點」。

前者是可驗證的事實，後者是推論。私有位址空間裡某台路由器剛好使用同一個網段並非不可能，此時前者仍然為真、只是把一條值得懷疑的線索交給使用者判斷，而後者會變成一句錯話。這也是上一項決策能成立的原因：措辭已經承擔了誤判，所以不必為精度付出讀取閘道的複雜度。

### 位址本身照舊回報，不隱藏也不改寫

熱點下若還有第三台裝置（另一支手機、平板），那個位址對它是有效的。隱藏位址會傷到這個情境，而這個情境正是「用手機當熱點、用平板當遙控」的合理用法。

警示與後續動作是**附加**在位址旁邊的欄位，不是位址的替代品。

### 呈現沿用探測階段既有的細節與後續動作樣式

警示文字套用階段細節的既有樣式類別，後續動作套用階段後續動作的既有樣式類別並同樣帶「→」前綴。位址那一行因此與四個階段講同一種話：這是細節、這是下一步。

不新增樣式規則，也不自創視覺語彙 —— 使用者已經在同一個面板裡學過這兩種文字的意義。

## Implementation Contract

**範圍邊界**

- 在範圍內：伺服器位址的判定與附加欄位、診斷回應中該欄位的形狀、控制介面對該欄位的呈現、專案文件的功能涵蓋表與說明。
- 不在範圍內：位址的取得方式、四個探測階段的輸出與三態語意、裝置清單、走路引擎、裝置寫入路徑、樣式表、控制面板的靜態 HTML 結構。本變更不得新增或修改任何 CSS 規則，不得新增或移除任何靜態 DOM 元素。

**後端：判定與回應**

診斷回應中伺服器位址的部分，除既有的主機位址與通訊埠外，在位址落在 `172.20.10.0/28`（即主機位址為 `172.20.10.` 開頭且最後一段介於 0 至 15）時另外帶有兩個字串欄位：一則警示與一則後續動作。位址不在該範圍、或位址為空字串時，這兩個欄位缺席，不得帶空字串。

警示文字為：

> 這個位址屬於 iPhone 個人熱點的網段。若這台 Mac 正連著手機的個人熱點，提供熱點的那支手機連不到熱點裡的用戶端，這個位址在它上面打不開。

後續動作文字為：

> 讓 Mac 與手機一起連到一般的 Wi-Fi 路由器。

主機位址與通訊埠的值不因此改變。

**前端：呈現**

位址那一行之後，警示與後續動作各自成為一個節點：警示套用階段細節的既有樣式類別，後續動作套用階段後續動作的既有樣式類別並以「→ 」開頭。兩個欄位缺席時不產生任何節點，也不留空行。

**失敗模式**

- 回應缺少這兩個欄位時，位址那一行照舊呈現，不產生額外節點，不拋出例外中斷診斷的呈現。
- 位址為空字串時（既有行為：取不到位址），維持既有的「無法判定本機位址」訊息，不附加警示。

**驗收條件**

- 位址為 `172.20.10.7` 時，回應帶有警示與後續動作兩個欄位，且文字與上述原文逐字相同。
- 位址為 `192.168.1.5` 時，回應不含這兩個欄位，且其餘輸出與變更前逐欄相同。
- 邊界：`172.20.10.0` 與 `172.20.10.15` 觸發提示；`172.20.10.16` 與 `172.20.11.1` 不觸發。
- 位址為空字串時不觸發提示，且「無法判定本機位址」的訊息照舊。
- 畫面上警示與後續動作出現在位址那一行之後，後續動作帶「→」前綴；欄位缺席時該區塊只有位址一行。
- 樣式表未被修改，控制介面的靜態元素 id 清單與變更前相同。

## Risks / Trade-offs

- **某台路由器可能剛好使用 `172.20.10.0/28`** → 此時會出現一則不適用的提示。措辭因此只陳述網段事實而不斷言拓撲，即使誤判那句話仍然為真；代價是提示比「確定是熱點」的版本弱一些，換來的是永遠不會說錯話。
- **熱點下的第三台裝置看到一則不適用於它的提示** → 位址對它有效，但提示會說「手機可能連不到」。保留位址已經照顧了它的主要需求；把提示收斂到「只在請求來自熱點主機時顯示」需要辨識請求來源，而診斷是使用者主動觸發的唯讀查詢，不該為此引入請求來源的判定。
- **判定只看位址、不看閘道** → 見上述決策。這是刻意用措辭換複雜度的取捨，不是疏漏。
- **這個提示不能解決問題，只能解釋問題** → 這個拓撲下沒有可用位址，真正的解法是換網路。診斷的職責是說明現狀與下一步，不是代替使用者改設定；四個探測階段的後續動作也都是這種性質。
