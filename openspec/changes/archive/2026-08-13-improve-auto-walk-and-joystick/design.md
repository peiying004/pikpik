## Context

這是一個單機執行的 iOS GPS 模擬器：Flask 提供網頁介面與 HTTP API，透過 `pymobiledevice3` 的 DVT／Instruments 通道對已連線的 iOS 裝置設定模擬座標。程式由兩個檔案構成 —— `app.py`（後端）與 `templates/index.html`（前端，含全部 CSS 與 JavaScript）。

現況的移動能力分為兩條獨立路徑：

- **搖桿路徑**：前端 `moveByJoystick` 每 100ms 依搖桿向量遞增標記座標，並經 `sendLocation` 呼叫 `/api/location`。座標運算與節流全在瀏覽器端。
- **自動移動路徑**：前端 `walkToMarker` 向外部路線規劃服務取得密集折線，送至 `/api/walk/start`；後端 `_walk_worker` 在背景執行緒中每 200ms 依 `speed_kmh` 在相鄰點之間插值前進，並將座標寫入裝置。前端 `startWalkPolling` 每 500ms 讀 `/api/walk/status` 把標記同步到伺服器算出的位置。

三項既有約束影響本次設計：

1. **Flask 為同步框架，`pymobiledevice3` 為 async**。專案以一條專屬背景執行緒承載 event loop（`_ensure_loop`），並用 `_run_async` 把 async 呼叫橋接成同步結果。所有裝置操作共用 `_dvt` 與 `_location_service` 兩個模組層級變數。
2. **`_walk_worker` 已經是通用的折線行走器**。它接受任意長度的座標序列，按設定時速在相鄰點之間插值，跨過中途點時不停頓。這正好是多座標依序移動所需的語意。
3. **專案沒有自動化測試**，`requirements.txt` 僅含三個執行期套件。驗收必須以可重現的手動操作步驟描述。

**實作後才發現的根因（本段為 ingest 補入）**：搖桿之所以不能用，不是手勢或重繪問題，而是 `nipplejs` 函式庫從未載入。頁面引用的路徑是該套件不存在的最小化檔名，實測回傳 404；該套件的 `package.json` 指向的是未最小化的檔名，實測回傳 200 且正確掛上全域物件。因此 `nipplejs.create` 必然拋出型別錯誤，而它位於前端腳本頂層敘述的中段 —— 錯誤讓它之後的所有頂層敘述全部不執行，包括搖桿事件綁定、搜尋框 Enter 鍵綁定、點擊外部關閉搜尋結果，以及頁面載入時的座標讀數與速度標籤初始化。函式宣告會提升，所以 `onclick` 綁定的按鈕仍可運作 —— 這正是故障能長期潛伏而不被察覺的原因。

## Goals / Non-Goals

**Goals:**

- 讓自動移動的預設時速有單一權威來源，前端未調整滑桿時送出的值與後端 fallback 必然一致。
- 讓使用者能一次輸入多個精準座標，按下開始後依輸入順序自動走完全程。
- 讓搖桿在觸控與滑鼠環境下都能真正拖動，且拖動期間介面不卡頓。
- 讓裝置定位寫入在長時間移動下保持穩定，且寫入失敗時使用者看得到，而不是介面顯示正常但裝置早已凍結。

**Non-Goals:**

- **不做道路路網規劃**。多座標移動採直線分段；穿越建築、水面、禁行區皆為可接受結果。既有「沿路走到這裡」按鈕仍使用外部路線規劃服務，本次不改動其路線來源。
- **不做中途點停留**。抵達中途點後立即接續前往下一點，不提供停留秒數設定。
- **不做座標清單的儲存、命名或重載**。輸入內容僅存在於當前頁面，重新載入即消失。
- **不改寫搖桿的座標運算位置**。搖桿仍在瀏覽器端計算位移，不搬到後端；本次只解決手勢獨佔與重繪卡頓。
- **不重構 event loop 橋接架構**。`_ensure_loop` 與 `_run_async` 的整體設計維持不變，只在裝置寫入路徑上補互斥與例外處理。
- **不新增自動化測試框架**。專案目前無測試基礎設施，導入測試框架屬於獨立範圍。

## Decisions

### 多座標移動採直線分段而非道路路網規劃

手動輸入座標的意圖是**精準落點**。道路路網規劃服務會把輸入座標吸附（snap）到最近的可行走道路上，位移可達數十公尺，使用者永遠抵達不到自己輸入的那個座標，與需求直接衝突。

替代方案是沿用「沿路走到這裡」既有的外部路線規劃服務，並以多 waypoint 形式一次取得貫穿所有點的路線。此方案路徑外觀較真實，但除了落點偏差外，還讓新功能繼承一個外部服務的可用性風險。

選擇直線分段：落點精準、無外部依賴、且不需要新的路線解析邏輯。

### 座標清單直接作為既有走行路線送出，複用插值邏輯

`_walk_worker` 已經按「相鄰兩點之間依時速插值、跨過中途點不停頓」運作，`_walk_state` 的進度欄位已代表「已抵達的路線點索引」與「路線總點數」。當送出的路線就是使用者的座標清單本身時，這些欄位天然等同於「第 N 點／共 M 點」。

因此不新增移動端點、不新增第二套行走器，也不在前端把座標展開成密集折線。`/api/walk/start` 的既有契約（接受座標序列與時速）保持不變，只是 payload 從密集折線放寬為稀疏的 waypoint 清單。

替代方案是在後端新增一個專責多座標的模組或端點。該層除了轉發到同一個行走器外不隱藏任何行為，刪掉它不會有任何功能損失，屬於不必要的間接層，故不採用。

### 起點為第一個座標，開始移動時先定位到該點

手動輸入的座標清單通常是一條完整路線，第一個座標即為預期起點。若改以「目前紅色標記位置」為起點，當標記離第一點很遠時會先產生一段冗長且非使用者意圖的移動。

`_walk_worker` 本來就以路線首點作為起始座標並在第一個週期即寫入裝置，此決策不需要額外邏輯。

### 開始移動時同步標記移動狀態，避免前端誤判為已結束

`/api/walk/start` 目前在啟動背景執行緒後立即回應，而移動中狀態是由該執行緒自己設定的。前端在收到回應後開始輪詢 `/api/walk/status`，若輪詢先於執行緒設定狀態抵達，前端會判定移動已結束並立刻送出停止請求，使用者看到的是「按了開始卻馬上停下」。

改為在 `/api/walk/start` 回應前就把移動中狀態、進度歸零與總點數設定完成，讓狀態在端點回應時即為真。同時在啟動新一輪移動時重置上一輪殘留的進度與裝置寫入狀態。

### 搖桿以手勢獨佔解除與地圖的衝突

**更正（ingest 補入）**：本決策原先被判定為「搖桿不能用」的根因，這是錯的。搖桿不能用的根因是函式庫從未載入（見 Context），搖桿物件根本不存在，因此手勢衝突連發生的機會都沒有。本決策處理的是一個真實但潛伏的缺陷 —— 函式庫修好、搖桿真正被建立之後，這個衝突才會浮現。決策本身保留，理由如下。

搖桿容器是浮在地圖之上的獨立絕對定位元素，並非地圖的子元素，因此地圖的手勢處理器仍會收到落在搖桿範圍內的指標與觸控事件。結果會是拖曳搖桿時地圖被平移，搖桿本身沒有跟隨或立即彈回。

解法是讓搖桿容器宣告不參與瀏覽器預設的觸控手勢，並阻擋指標、觸控與滾動事件向底層地圖傳播。地圖函式庫本身提供阻擋傳播的工具函式，優先使用該工具而非自行攔截，以確保涵蓋其內部監聽的完整事件集合。

替代方案是把搖桿改為地圖的自訂控制項（control），由地圖統一管理事件。此方案較徹底，但需要重寫搖桿的建立與定位流程，超出「修復現有功能」的範圍。

### 搖桿的地圖跟隨改為無動畫，並移除搖桿容器的背景模糊

搖桿驅動的地圖跟隨目前每 100ms 就啟動一次帶動畫的平移，前一次動畫尚未結束即被新的取代，動畫狀態持續堆疊。同時搖桿容器套用背景模糊效果，地圖每次重繪都必須重算模糊區域，形成每秒十次的全區重繪。兩者疊加造成操作黏滯與放開後仍在飄移。

改為以無動畫方式直接設定地圖視野（動畫在 100ms 的更新頻率下不具視覺意義，位置更新本身已足夠連續），並移除搖桿容器的背景模糊。搖桿容器保留半透明底色，視覺變化極小。

### 裝置定位寫入以互斥鎖序列化，並丟棄重疊的寫入

`_set_location` 在寫入失敗時會依序關閉再重建連線，過程中改寫 `_dvt` 與 `_location_service` 兩個共用變數。移動期間每 200ms 就有一個新的寫入協程被排入 event loop 且不等待結果，因此多個協程會同時進入這段重連流程：其中一個剛建好連線，另一個的關閉步驟隨即把它關掉，最終共用變數指向一個底層通道已關閉的服務，之後每次寫入都失敗、每次失敗又觸發新一輪重連。

短路線幾乎不觸發重連所以症狀不顯；長時間的多座標移動必然遭遇連線老化，屆時重連機制本身即成為故障放大器。

三項處置：

1. **互斥**：以模組層級的 async 互斥鎖包住 `_set_location` 的寫入與重連流程，確保任一時刻只有一個協程能改寫共用連線變數。
2. **丟棄而非排隊**：移動期間若前一次寫入尚未完成，跳過本次寫入。座標以每個週期約一公尺的間距推進，較新的座標本身即包含較舊座標的資訊，丟棄舊寫入不會造成位置錯誤；相對地無上界排隊會讓裝置位置離顯示位置愈來愈遠。
3. **不再吞掉例外**：移動路徑上的寫入協程目前以「排入即忘」方式送出，協程內部拋出的例外被收在無人取用的 Future 中，永不顯現；端點外圍的例外處理只涵蓋排程本身，抓不到協程內部的錯誤。改為在協程完成時取出其例外並記錄。

### 裝置寫入狀態納入移動狀態回報，使失敗可見

移動中的顯示位置來自 `_walk_state` 的純數學插值，與裝置寫入是否成功完全無關。前端把它讀來當標記位置，因此裝置寫入全部失敗時，網頁上的標記仍會平滑走完全程、移動中狀態仍為真、裝置連線指示仍顯示已連接 —— 使用者不去看手機就無從察覺。

在移動狀態中加入「最近一次裝置寫入是否成功」與「最近一次失敗訊息」兩項資訊，由前端在輪詢時呈現，讓靜默故障成為可見故障。

### 預設時速以後端為權威來源，前端初始化時對齊

預設時速目前散落在後端的移動狀態初值與端點 fallback、以及前端的滑桿屬性、顯示文字與 JavaScript 變數，共四處。任一處漏改即造成「使用者沒動滑桿時，前端送出的值與後端 fallback 不同」。

本次仍以直接修改四處數值的方式對齊為 18，不引入設定檔或組態端點 —— 這是個單機工具，額外的組態層會增加啟動複雜度而無實際收益。但前端的顯示文字與 JavaScript 變數改為在頁面初始化時從滑桿當前值推導，使滑桿屬性成為前端內部的單一來源，把四處收斂為兩處（後端一處、前端一處）。

### 修正搖桿函式庫的引用路徑，不改版本

該套件的 `package.json` 明確指向未最小化的檔名，而頁面引用的是不存在的最小化檔名。修法是把引用路徑改成套件實際提供的檔名，版本維持不變 —— 現有的搖桿程式碼是針對這個版本寫的，換版本會引入不必要的相容性風險。

替代方案是把函式庫收進專案自帶的靜態檔案目錄，徹底消除 CDN 路徑與版本的脆弱性。此方案更穩固，但地圖圖磚本來就需要連網，拿不到完整離線的好處，且會改變專案的檔案結構與載入流程。本次不採用，留待需要時另開變更。

### 僅依賴 DOM 的初始化提前到函式庫初始化之前

座標讀數與速度標籤的初始化只需要 DOM，卻被放在前端腳本的最後，因此任何在它之前發生的錯誤都會讓它們留在未填值的狀態。速度標籤在本次變更中改為由滑桿值推導（見預設時速決策），因此這個順序問題從「不易察覺」變成「使用者直接看到空白數字」。

改為把這類初始化移到宣告區之後、任何第三方函式庫初始化之前。這個順序規則本身就是契約：不依賴函式庫的東西，不應該被函式庫的失敗拖累。

替代方案是在速度標籤的 HTML 裡保留一份寫死的預設文字當後備。這會讓預設值又回到兩處，與「滑桿是前端唯一來源」的決策衝突，故不採用。

### 函式庫載入失敗必須可見，且不擴散到其餘初始化

這次故障能長期潛伏，是因為它完全無聲：使用者看到的是搖桿不動、速度數字空白、Enter 鍵沒反應，三個看似無關的症狀，沒有任何一處指向真正的原因。

改為在建立搖桿的呼叫外圍加上防護：函式庫不可用時，在畫面上顯示搖桿不可用的提示，並讓後續初始化繼續執行。這樣單一函式庫失效只會損失搖桿本身，而不會連帶癱瘓搜尋、速度顯示與座標讀數。

## Implementation Contract

#### 行為

**預設時速**

- 頁面載入時，自動移動速度滑桿位於 18，其下方文字顯示 `18 km/h`。
- 使用者未觸碰滑桿即開始移動時，移動以 18 km/h 進行。
- 請求未帶時速欄位時，後端以 18 km/h 進行移動。

**多座標依序移動**

- 介面提供一個多行文字輸入區與一個「開始移動」按鈕。
- 輸入格式為每行一組座標，緯度與經度以逗號分隔。空白行與行首行尾空白忽略。
- 按下「開始移動」後：裝置立即定位到第一個座標；接著以滑桿設定的時速沿直線移動到第二個座標，抵達後不停頓、立即接續前往第三個座標，依此走完清單；抵達最後一個座標後移動自動結束。
- 地圖上繪製依序編號的座標標記與依序連接的折線，並將視野調整至涵蓋全部座標。
- 移動期間顯示目前進度為「第 N 點／共 M 點」，N 為已抵達的座標序號。
- 移動期間可按停止移動中止；中止後清除折線與編號標記。

**搖桿**

- 頁面載入後搖桿確實存在並可操作（在函式庫修正前它根本沒有被建立）。
- 在搖桿範圍內按住並拖曳時，搖桿跟隨指標移動，底層地圖不因此手勢平移或縮放。
- 拖曳期間標記持續移動、地圖持續跟隨，操作無可感知的黏滯；放開後標記立即停止，不繼續飄移。
- 搖桿函式庫不可用時，畫面顯示搖桿不可用的提示，且頁面其餘功能（速度標籤、座標讀數、搜尋 Enter 鍵、多座標移動）全部照常運作。

**前端啟動順序**

- 頁面載入完成、使用者尚未進行任何操作時，底部的座標讀數即顯示數值而非佔位符號，速度標籤即顯示數值。
- 在搜尋框輸入後按 Enter 會執行搜尋；點擊搜尋結果面板以外的區域會關閉結果清單。這些行為不受第三方函式庫是否載入成功影響。

**裝置寫入**

- 移動期間裝置寫入失敗時，介面顯示裝置寫入失敗的提示與最近一次的失敗訊息，而非維持一切正常的外觀。
- 連線老化觸發重連時，重連流程不與其他寫入交錯，重連成功後移動繼續。

#### 介面與資料形狀

- `/api/walk/start` 的請求契約不變：接受一個座標序列欄位與一個時速欄位。多座標移動送出的座標序列即為使用者輸入的座標清單本身，不預先展開為密集折線。既有的「至少兩點」驗證繼續適用。
- `/api/walk/status` 的回應在既有欄位（移動中、目前緯經度、進度索引、路線總點數、時速）之外，新增兩個欄位：最近一次裝置寫入是否成功（布林），以及最近一次裝置寫入的失敗訊息（字串，無失敗時為空）。
- `/api/walk/start` 在回應前即完成移動中狀態、進度歸零、總點數與裝置寫入狀態的設定，使其回應後的首次狀態查詢即反映真實狀態。
- `_set_location` 的呼叫端契約不變（傳入緯度與經度、以協程形式執行），新增的互斥為其內部實作細節。
- 搖桿容器與速度控制面板的 DOM 結構與既有 CSS 類別名稱不變。
- 搖桿函式庫的引用改為該套件實際提供的未最小化檔名，版本不變。判斷路徑正確的依據是該 URL 回傳 200 且在瀏覽器中掛上對應的全域物件。

#### 失敗模式

- **座標解析失敗**：任一非空行無法解析為兩個數值、或緯度超出 -90 至 90、或經度超出 -180 至 180 時，不啟動移動，並顯示指出出錯輸入行序號與原因的訊息。
- **有效座標少於兩個**：不啟動移動，顯示需要至少兩個座標的訊息。既有後端驗證作為第二道防線，前端先行檢查以提供更明確的訊息。
- **裝置寫入失敗**：移動不中斷（插值持續進行），失敗狀態經移動狀態回報給前端顯示，並在伺服器端記錄。此為刻意選擇 —— 使用者可能在裝置暫時斷線後重新連上，中止整趟移動的代價高於繼續嘗試。
- **重連失敗**：視為裝置寫入失敗處理，不使移動執行緒終止。
- **重疊寫入**：前一次寫入未完成時本次寫入被丟棄，此為預期行為，不記為失敗、不回報為錯誤。
- **搖桿函式庫不可用**：不建立搖桿，在畫面上顯示搖桿不可用的提示，其餘初始化繼續完成。此為刻意選擇 —— 讓單一函式庫失效只損失搖桿，而不是靜默癱瘓半個頁面。
- **其他第三方函式庫不可用**：不在本次範圍內處理個別退化行為，但僅依賴 DOM 的初始化因為排在函式庫之前，仍會完成。

#### 驗收標準

專案無自動化測試，以下為手動驗證步驟。每項須實際觀察到所述結果。

1. **預設時速**：載入頁面，確認自動移動速度滑桿顯示 `18 km/h`。不觸碰滑桿，執行一次多座標移動，確認伺服器端記錄的移動起始訊息顯示速度為 18 km/h。
2. **多座標依序抵達**：輸入三個相距數百公尺的座標，開始移動。確認裝置先出現在第一個座標；確認標記依序經過第二、第三個座標；確認經過第二個座標時沒有停頓；確認抵達第三個座標後移動自動結束且按鈕復原。
3. **進度回報**：同上情境，確認移動期間進度顯示由「第 1 點」依序變為「第 2 點」、「第 3 點」，總數顯示為 3。
4. **座標解析錯誤**：在三行有效座標中插入一行 `25.03, abc`，按開始移動。確認移動未啟動，且錯誤訊息指出是第幾行有問題。
5. **座標數量不足**：僅輸入一行座標，按開始移動。確認移動未啟動並顯示需要至少兩個座標。
6. **搖桿手勢獨佔**：在搖桿上按住並拖曳。確認搖桿跟隨指標、標記持續移動、且地圖沒有因該手勢被平移。在觸控環境重複一次。
7. **搖桿無卡頓**：持續拖曳搖桿十秒。確認標記移動連續、無可感知停頓；放開搖桿後確認標記在一個更新週期內停止，不繼續飄移。
8. **開始移動不誤判結束**：連續執行五次多座標移動。確認每次都持續移動，沒有出現按下開始後立即停止的情形。
9. **裝置寫入失敗可見**：開始一次多座標移動後，中斷裝置連線（拔除或停止裝置隧道服務）。確認介面在數秒內顯示裝置寫入失敗與失敗訊息，而非維持裝置已連接的外觀。
10. **重連互斥**：承上，重新恢復裝置連線。確認介面回報恢復正常、裝置位置重新跟上標記位置，且伺服器端記錄中沒有出現連續不斷的重連訊息。
11. **搖桿函式庫路徑**：對頁面引用的搖桿函式庫 URL 發出請求，確認回傳 200 而非 404。
12. **搖桿確實存在**：重新載入頁面，確認搖桿在右下角出現且可拖動；開啟瀏覽器主控台，確認沒有與搖桿函式庫相關的錯誤。
13. **啟動順序**：硬性重新載入頁面，在碰任何東西之前確認底部座標讀數顯示數值、自動移動速度標籤顯示 `18 km/h`；在搜尋框輸入後按 Enter 確認會執行搜尋。
14. **函式庫失效隔離**：暫時把搖桿函式庫的引用改成一個不存在的路徑後重新載入，確認畫面顯示搖桿不可用的提示，且速度標籤、座標讀數、搜尋 Enter 鍵、多座標移動全部照常運作。驗證後把引用改回正確路徑。

#### 範圍邊界

**在範圍內：**

- `app.py`：自動移動預設時速、移動啟動時的狀態初始化、移動狀態新增裝置寫入回報欄位、`_set_location` 的互斥與重連保護、移動路徑上寫入協程的例外取出與記錄、重疊寫入的丟棄。
- `templates/index.html`：搖桿函式庫的引用路徑、前端啟動順序（僅依賴 DOM 的初始化先行）、搖桿函式庫失效時的可見提示與隔離、座標清單輸入介面與開始移動流程、座標解析與錯誤訊息、依序編號標記與折線繪製、進度與裝置寫入狀態的顯示、搖桿容器的手勢獨佔樣式與事件阻擋、搖桿地圖跟隨改為無動畫、搖桿容器移除背景模糊、速度滑桿預設值與初始化對齊。

**在範圍外：**

- 既有「沿路走到這裡」按鈕的路線來源與行為（除了共用的預設時速與裝置寫入修正所帶來的間接改善）。
- 搖桿座標運算搬移至後端。
- 中途點停留、座標清單持久化、道路路網規劃。
- `_ensure_loop` 與 `_run_async` 的橋接架構重構。
- 版面在小螢幕上的重疊問題（速度控制面板與搖桿使用固定像素偏移）。
- 自動化測試框架的導入。
- 把第三方前端函式庫收進專案自帶的靜態檔案目錄（vendoring）。本次只修正引用路徑。
- 其他第三方函式庫（地圖函式庫、地圖圖磚服務）各自的載入失敗退化行為。

## Risks / Trade-offs

- **直線路徑會穿越建築、水面與禁行區** → 已與需求提出者確認為可接受。此工具的使用情境是精準抵達指定座標，路徑真實感不是目標。若日後需要真實路徑，可在保留直線模式的前提下另加一個路網模式，不影響本次契約。
- **座標間距很大時，單段移動時間極長** → 以 18 km/h 走 10 公里需約 33 分鐘，期間使用者除了停止移動外沒有跳段的手段。本次不提供跳段功能；進度顯示「第 N 點／共 M 點」讓使用者至少能判斷目前處於哪一段。
- **丟棄重疊寫入會讓裝置位置略微落後顯示位置** → 落後幅度受單次寫入耗時限制，在每週期約一公尺的推進速率下影響極小，且遠優於無上界排隊造成的持續累積落後。
- **互斥鎖使裝置寫入完全序列化** → 若單次寫入耗時超過移動週期，實際寫入頻率會低於每週期一次。這是刻意的取捨：位置更新頻率下降只影響平滑度，而共用連線變數被並行改寫會導致整趟移動失效。
- **新增的裝置寫入回報欄位只在移動期間更新** → 搖桿路徑的裝置寫入狀態仍走既有的連線指示邏輯，兩條路徑的狀態呈現不完全一致。本次不統一，以免把範圍擴大到搖桿的狀態回報重構。
- **移除搖桿容器的背景模糊會改變視覺外觀** → 保留半透明底色，變化限於背景是否模糊。以可用性換取極小的視覺退讓。
- **無自動化測試，驗收完全依賴手動步驟** → 驗收標準已寫成十四項可重現的具體觀察，其中裝置相關項目需要實體 iOS 裝置與裝置隧道服務。無裝置時第 9、10 項無法執行，須明確記錄為未驗證，不得標記為通過。
- **靜態檢查與 stub 執行無法取代一次真實的頁面載入** → 這是本次最重要的教訓。第一輪實作把搖桿相關任務標記為完成，依據是 CSS 屬性的靜態比對與在 stub 環境中執行前端腳本；但 stub 環境自行提供了一個假的搖桿函式庫，正好繞過真正的故障點，導致「函式庫 404」這個根因完全沒被發現。凡是涉及第三方函式庫載入、或需要在瀏覽器中觀察的行為，驗收必須包含一次真實頁面載入並檢視主控台，不得以靜態比對結案。
- **既有的搖桿手勢與卡頓修正尚未在真實環境驗證** → 第 4 組任務（手勢獨佔、無動畫跟隨）在函式庫修好之前不可能被觀察到，其驗收實際上從未通過。這些任務保留為已完成（程式碼確實已寫入），但驗收標準第 6、7 項必須在函式庫修正後重新執行一次。
- **搖桿函式庫仍依賴外部 CDN** → 修正路徑後仍可能因該服務中斷或套件下架而失效。本次以「失效時可見且不擴散」降低衝擊，而非消除依賴；若這類中斷反覆發生，再評估 vendoring。
