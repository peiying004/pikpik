## Context

專案有兩層說明性資料，維護機制完全不同：

- `openspec/specs/` 下的五份規格描述系統行為，由封存流程自動套用 delta，因此始終與最近一次封存的變更同步。
- docs 目錄下的兩份文件描述系統構成與程式碼，只能靠人手動更新。

2026-07-16 之後程式碼改過四輪（統一控制面板、改善自動移動與搖桿、函式庫與錯誤回報一致性、走路端點與輸入驗證），規格四次都同步了，文件四次都沒有。

以現行程式碼盤點，26 項功能中 4 項在文件裡正確、9 項過時或寫錯、13 項完全沒有。

文件之所以腐爛得比規格快，關鍵在**耦合的粒度**：規格描述行為（「裝置收到的第一個座標與路線的第一個座標相同」），行為不變時規格就不需要改；文件嵌入程式碼片段（四十行的走路迴圈），任何一行實作變動都會讓片段失真。同一份文件裡，Haversine 公式的片段四輪下來一次都沒錯過，走路迴圈的片段三輪錯了三次。

## Goals / Non-Goals

**Goals:**

- 兩份文件涵蓋程式碼現有的每一項功能。
- 文件中不存在與程式碼牴觸的事實陳述。
- 涵蓋度可以用文字搜尋驗證，而不是靠審閱者的判斷。
- 降低下一次程式碼變動造成文件失真的機率。

**Non-Goals:**

- 不重排章節結構、不刪除文件、不修改程式碼、不建立自動產生機制、不新增文件入口、不處理版本控制。理由見提案的 Non-Goals 段落。
- 不要求文件重述規格檔已經寫清楚的行為細節。文件指出功能存在與它在架構中的位置，行為契約留在規格檔。
- 不為文件建立自動化的持續檢查（例如提交前掛鉤）。本變更只確立可執行的檢查方式，把它接進流程是獨立的決定。

## Decisions

### 程式碼片段的去留以「是否隨行為變動而改寫」為分界

保留的片段必須同時滿足兩個條件：不超過十五行，且它表達的是一個不隨功能演進而改變的觀念。Haversine 距離公式、座標傳送的節流結構屬於這一類，四輪變動下來從未失真。

移除的片段改寫為「函式名加行為描述」：點名負責的函式，說明它負責什麼、與相鄰函式如何分工，細節指向程式碼。走路工作執行緒、裝置座標注入、地圖與搖桿初始化、搜尋結果渲染、走路輪詢屬於這一類。

考慮過的替代方案：全部保留並逐段更新。否決的理由是這是造成目前狀況的作法，四輪之後十三段片段中多段已經錯誤；同一份文件裡穩定片段與易腐片段的失真率差異明顯，沒有理由用同一種形式對待兩者。

考慮過的替代方案二：全部移除，文件完全不含程式碼。否決的理由是穩定片段的閱讀價值高而維護成本近乎為零，一併移除是為了規則整齊而犧牲可讀性。

### 涵蓋度以功能與關鍵詞的對照表驗證

規格檔中列出一張表，每一列是一項功能，配一個在文件中唯一且穩定的檢查關鍵詞。驗收方式是對 docs 目錄搜尋每一個關鍵詞，每一個都必須至少命中一次。另有一組必須零命中的關鍵詞，用來擋住已知的事實錯誤復發。

關鍵詞的選擇原則：優先使用程式碼中的識別字（函式名、常數名、狀態欄位名），因為它們在文件中出現時幾乎必然伴隨對該功能的說明；沒有合適識別字時使用該功能的中文名稱。

考慮過的替代方案：以審閱者逐項確認取代關鍵詞搜尋。否決的理由是使用者要的是「確認文件沒缺失」，判斷題無法在下一次變更時重跑，而搜尋可以。

### 多座標依序移動在架構文件中獨立成一張資料流圖

架構文件目前只有一張自動沿路行走的資料流圖，畫的是單點沿路移動：向路線規劃服務取得道路座標後交給後端。多座標依序移動走的是同一個走路端點，但前段完全不同：座標由使用者逐行輸入、在前端解析與驗證、不經過任何外部服務、不吸附道路。

新增一張獨立的圖，而不是在現有圖上加分支。兩條路徑只在「送出走路開始請求之後」才合流，把差異塞進同一張圖會讓兩條都難讀。

### 事實錯誤的修正與涵蓋度分開驗收

兩處事實錯誤（相依清單中已移除的套件、座標注入函式缺少互斥保護）以「必須零命中」與「必須命中」兩組關鍵詞分別把關，不與十三項新增功能的涵蓋度混在同一條驗收裡。錯誤復發與涵蓋不足是不同的失效模式，混在一起會讓失敗訊息無法指出原因。

## Implementation Contract

**行為**

- 兩份文件更新後，規格涵蓋表列出的 30 個檢查錨點在 docs 目錄下各自至少命中一次（盤點時的 26 項功能在寫規格時細分為 30 個可獨立檢查的錨點）。
- 必須零命中的關鍵詞在 docs 目錄下完全不出現。
- 架構文件包含一張多座標依序移動的資料流圖，且該圖不含任何外部路線規劃服務的參與者。
- 架構文件的分層架構表現層列出控制面板與多座標依序移動。
- 架構文件的關鍵設計決策表包含最近三輪變更確立的六項決策：重疊寫入丟棄而非排隊、路線起點與終點是丟棄規則的具名例外、寫入完成回呼以代次辨識輪次、裝置寫入結果三態、第三方函式庫失效必須在頁面上可見、走路輸入驗證前置於啟動工作執行緒。
- 架構文件的目錄結構包含 openspec、.spectra、.spectra.yaml、CLAUDE.md、.claude 五個項目。
- 程式碼介紹文件不再包含超過十五行的程式碼片段；保留的片段限於 Haversine 距離公式與座標傳送節流結構。
- 程式碼介紹文件的全域狀態一節列出裝置寫入互斥鎖、寫入逾時常數、寫入進行中旗標、最後送達座標、走路代次五個項目。

**介面與資料形狀**

- 兩份文件的檔名與所在目錄不變。
- 兩份文件的既有章節標題與編號不變，允許在既有章節之下新增小節，允許在架構文件新增一張圖。
- 規格檔新增一個能力目錄，名稱為 project-documentation。

**失敗模式**

- 檢查關鍵詞命中零次表示該功能未被涵蓋，該項驗收失敗，並可從關鍵詞直接指出是哪一項功能。
- 必須零命中的關鍵詞出現，表示已修正的事實錯誤復發。

**驗收條件**

- 對 docs 目錄逐一搜尋規格檔對照表中的每一個必須命中關鍵詞，記錄命中次數，全部大於零。
- 對 docs 目錄搜尋必須零命中關鍵詞，命中次數為零。
- 以文字搜尋確認程式碼介紹文件中不存在超過十五行的程式碼區塊。
- 閱讀架構文件的多座標依序移動資料流圖，確認參與者不含外部路線規劃服務。
- 逐一比對六項關鍵設計決策是否都出現在架構文件的決策表中。

**範圍界線**

- 在範圍內：docs 目錄下兩份文件的內容、新增的 project-documentation 規格。
- 在範圍外：app.py、templates/index.html 與其他任何程式碼；文件的章節結構重排；README 或文件入口；自動產生文件的工具；文件檢查的自動化掛鉤；版本控制。

## Risks / Trade-offs

- 移除長程式碼片段後，讀者要理解實作細節必須打開程式碼 → 被移除的片段對應的函式在程式碼中都有密集的「為什麼」型註解，內容比原本的片段更完整；文件改為點名函式，等於把讀者導向更好的來源。
- 關鍵詞搜尋只能證明「文件提到了這個功能」，不能證明「說明是正確的」 → 這個限制是明確的，關鍵詞把關的是涵蓋度，正確性由撰寫時對照程式碼保證；必須零命中的那一組則專門擋事實錯誤復發。
- 關鍵詞選用程式碼識別字時，識別字改名會讓檢查失效 → 這是刻意的：識別字改名本身就代表實作變動，檢查失敗正好提醒文件需要同步。
- 文件仍然沒有自動同步機制，下一輪程式碼變更仍可能造成漂移 → 本變更把漂移從「無法察覺」變成「可用一條指令察覺」，把檢查接進流程留給後續決定。
