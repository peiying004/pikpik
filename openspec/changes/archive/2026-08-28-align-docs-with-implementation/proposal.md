## Summary

把 docs 目錄下的兩份專案文件與現行程式碼對齊，並把「文件涵蓋程式碼所有功能」變成一條可以用指令檢查的要求，而不是憑感覺判斷的判斷題。

## Motivation

兩份文件停在 2026-07-16，程式碼在那之後改過四輪。以現行程式碼的功能逐項比對，26 項功能中只有 4 項在文件裡是正確的，9 項過時或寫錯，13 項完全沒有。

過時本身不是最嚴重的問題，有兩類更具體的傷害：

**一、文件展示的舊程式碼會誤導維護者。** 程式碼介紹文件中的走路工作執行緒片段，展示的是一個沒有起點寫入、沒有終點補寫、沒有重疊寫入丟棄、沒有寫入完成回呼、沒有代次辨識的迴圈。那段片段語法正確、註解完整，看起來就是現在的程式碼。照著它修改，會把最近三輪修好的缺陷全部改回去。

**二、有兩處是事實錯誤而非單純陳舊。** 架構文件把已經從相依清單移除的 timezonefinder 列為必要套件；程式碼介紹文件展示的裝置座標注入函式沒有互斥保護，而互斥保護是 2026-08-13 就加上的，缺少它會讓多個協程互相關閉對方剛建立的連線。照著這兩處安裝環境或除錯的人會直接走錯路。

**三、四個功能區塊從未被寫入文件。** 統一控制面板與收合、多座標依序移動的完整流程、裝置寫入結果三態、第三方函式庫載入失敗的守衛與降級提示。其中多座標依序移動自 2026-08-13 起就是主要功能之一。

結構性的成因是：規格檔由封存流程自動套用 delta 而保持同步，文件沒有任何對應機制，只能靠人記得更新，而四輪都沒有記得。

## Proposed Solution

- 保留兩份文件與現有章節骨架，逐節更新內容，不重排結構。
- 補齊十三項從未寫入文件的功能，其中多座標依序移動在架構文件中新增一張資料流圖。
- 修正兩處事實錯誤：相依套件清單與座標注入函式的互斥保護。
- 把易腐的長程式碼片段改為「函式名加行為描述」，短而觀念穩定的片段保留。分界線寫進設計文件。
- 新增一項描述專案文件本身的能力，把「文件必須涵蓋程式碼的每一項功能」寫成規範性要求，並附一張功能與檢查關鍵詞的對照表，讓涵蓋度可以用文字搜尋驗證。

## Non-Goals

- **不重排兩份文件的章節結構。** 現有骨架是可用的，內容過時與結構無關；為了改內容順便重排會讓差異難以審閱。
- **不刪除任何一份文件。** 儘管程式碼註解的密度與品質高於文件，兩者的用途不同：註解回答「這一行為什麼這樣寫」，文件回答「這個系統由哪些部分組成、資料怎麼流動」。
- **不修改任何程式碼。** 本變更只動 docs 目錄與規格檔，不觸及 app.py 與前端頁面。
- **不建立自動產生文件的機制。** 從程式碼自動抽出文件需要額外工具與建置步驟，而這個專案只有兩個原始檔；用一張可搜尋的對照表就能達到同樣的把關效果，成本低得多。
- **不新增 README 或文件入口。** 目前沒有任何地方連到 docs 目錄，補上入口是獨立的決定，與本變更的涵蓋度目標無關。
- **不處理專案沒有版本控制這件事。**

## Alternatives Considered

**照原樣更新，保留所有程式碼片段。** 否決的理由是這正是造成目前狀況的作法：文件嵌了十三段程式碼，四輪改動後其中多段已經錯誤，而且錯得很有說服力。保留同樣的形式等於預約下一次腐爛。

**刪除程式碼介紹文件，只留架構圖，程式碼細節交給註解。** 否決的理由是文件與註解回答的問題不同，讀者需要一份能看到整體構成的入口，而註解只在打開特定檔案時才讀得到。

**從程式碼自動產生文件。** 否決的理由是成本與規模不成比例，見 Non-Goals。
