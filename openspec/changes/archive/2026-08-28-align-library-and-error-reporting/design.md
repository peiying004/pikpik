## Context

這個專案是一支在瀏覽器操作、由 Flask 後端寫入 iOS 裝置模擬定位的工具。前端單檔 templates/index.html 以傳統 script 標籤載入兩個第三方函式庫：地圖函式庫 Leaflet 與搖桿函式庫 nipplejs，兩者皆由 CDN 提供，沒有本地備援。

前一輪變更（已封存的 improve-auto-walk-and-joystick）處理過一次「函式庫載入失敗導致半個頁面靜默失效」的事故：當時 nipplejs 的引用路徑指向不存在的 .min.js，建立搖桿時拋出的例外中斷了整個頂層腳本，使用者看到的是速度標籤空白、座標讀數停在佔位符號、搜尋框 Enter 沒反應這三個彼此看似無關的症狀。該次修正加上了 nipplejs 的可用性檢查與可見提示，並把純 DOM 的初始化提到腳本最前面。

本次變更處理的是那次修正沒有涵蓋到的兩個同型缺口：

1. Leaflet 沒有任何可用性檢查。建立地圖的敘述是裸呼叫，一旦函式庫沒載入就會在頂層拋錯並中斷其後所有敘述。更棘手的是，nipplejs 的可用性檢查排在建立地圖之後，所以 Leaflet 失敗會連帶讓搖桿的提示也不會出現 —— 上一輪修好的可見性在這條路徑上等於沒有。
2. 裝置寫入失敗的原因在自動移動路徑上經由走路狀態完整回報，但在單點寫入路徑上，前端讀取的回應欄位名與後端實際回傳的欄位名不一致，導致原因永遠取不到，一律退回固定文字。

此外，走路狀態的裝置寫入結果目前只有成功與失敗兩態，且在移動啟動時被初始化為成功。前端第一次輪詢很可能在任何寫入結果回來之前就發生，於是介面在毫無根據的情況下宣稱裝置已連接。

## Goals / Non-Goals

**Goals:**

- 兩個第三方函式庫的載入失敗都能被使用者看見，且任一個的失敗不會遮蔽另一個的失敗回報。
- 地圖函式庫不可用時，不依賴地圖的功能（座標讀數、速度標籤、搜尋框 Enter、點擊外部關閉結果）維持可用；依賴地圖的控制項以停用狀態呈現，而不是按下去在主控台丟出例外。
- 裝置寫入失敗的原因在單點寫入路徑上與自動移動路徑上一樣可見。
- 介面不在缺乏根據時宣稱裝置已連接。
- 順手清掉三項低風險的既有問題：搜尋結果的未跳脫插入、開發伺服器的除錯器對外綁定、死碼與未使用相依。

**Non-Goals:**

- **不為地圖函式庫失效提供功能性降級。** 地圖、標記、搖桿移動、路線繪製、多座標移動全都經由地圖函式庫的物件運作，沒有它就沒有可以退而求其次的替代路徑，硬做只會得到一個轉了沒有作用的搖桿。規格要求的是「說出哪個控制項不可用」，不是「功能仍然可用」。
- **不引入通用的函式庫載入檢查抽象層。** 全頁只有兩個第三方函式庫，兩個各自的具名檢查比一層 helper 更好讀，也更容易寫出貼切的訊息。
- **不改動既有 HTTP 端點的路徑、請求格式或既有欄位名稱。** 單點寫入的失敗原因採對齊前端讀取欄位的方式解決，不是改後端。
- **不處理自動移動的收尾與輸入驗證。** 終點座標的強制寫入、終點進度的可見性、後端對路線與速度的型別驗證，這三項會動到走路工作執行緒的迴圈與時序，與本變更的改動面沒有重疊，留給後續變更。
- 不加入自動化測試框架。本專案目前沒有測試基礎建設，本變更的驗收採手動與靜態檢查。

## Decisions

### 地圖函式庫失效時採明確告知，不做假降級

建立地圖之前先檢查地圖函式庫的全域物件是否存在，不存在就在地圖區域顯示一段訊息，指出地圖、標記與移動功能不可用及其可能原因，並跳過所有地圖相依的初始化。

考慮過的替代方案：把建立地圖包在例外捕捉裡，捕捉後讓其餘敘述照常執行。否決的理由是地圖物件與標記物件被其後數十處引用，捕捉例外只會把一次頂層中斷換成一連串執行期的空值存取，症狀更分散、更難診斷。既然沒有可用的替代路徑，就該在單一位置說清楚，而不是讓失敗沿著呼叫點擴散。

### 搖桿可用性檢查與地圖初始化解耦

搖桿的可用性檢查與不可用提示，要排在地圖初始化之前，且不得依賴地圖函式庫的任何符號。地圖相依的手勢傳播阻擋（目前對搖桿容器與控制面板各做一次）留在地圖初始化成功的分支裡。

這樣一來四種組合都有正確行為：兩個函式庫都在（一切正常）、只有地圖掛掉（地圖訊息＋搖桿不可用提示）、只有搖桿掛掉（維持現行行為）、兩個都掛掉（兩則訊息都出現）。

### 地圖不可用時停用相依控制項並保留純 DOM 功能

地圖不可用時，把依賴地圖或標記的控制項設為停用：設定 GPS 位置、置中標記、開始移動、停止移動、沿路走到這裡。這是一份可以列舉窮盡的清單，不需要通用機制。

搜尋維持可用：送出查詢與顯示結果都不碰地圖。選取結果時，更新座標讀數與記憶體中的座標值，跳過標記與地圖視野的更新。這讓既有規格「函式庫失效後 Enter 鍵搜尋仍然可用」這條在地圖函式庫失效時同樣成立。

考慮過的替代方案：不停用，讓使用者按下去時得到例外。否決的理由是規格要求「使用者不會只看到不相干的症狀」，一個按了沒反應又在主控台丟錯的按鈕正是那種症狀。

### 裝置寫入失敗原因對齊後端既有欄位名

單點寫入的回應在失敗時帶有一個描述失敗原因的欄位，前端目前讀的是另一個從未存在的欄位名。修正方向是改前端讀取後端實際回傳的那個欄位，後端不動。

考慮過的替代方案：改後端改用前端目前讀取的欄位名。否決的理由是後端在自動移動路徑上已經用同一組命名回報寫入失敗訊息，改後端會讓兩條路徑的命名分岔；而且那是對外契約，改動成本大於收益。

### 裝置寫入結果改為三態

走路狀態中表示裝置寫入結果的欄位，由布林的成功／失敗擴充為三態：尚未有結果、成功、失敗。移動啟動時初始化為「尚未有結果」，第一個寫入完成回呼依結果覆寫為成功或失敗。

前端只在讀到明確的成功時才顯示裝置已連接並點亮狀態圓點；讀到明確的失敗時沿用現行的失敗顯示與訊息；讀到「尚未有結果」時顯示等待裝置回應，狀態圓點維持未點亮。

考慮過的替代方案：讓前端在移動剛開始的前幾次輪詢忽略這個欄位。否決的理由是那是用時間長度猜測狀態，裝置慢一點就會猜錯；把「還不知道」明確表示成一個狀態，前端就不需要猜。

### 搜尋結果以文字節點插入

地點搜尋結果的顯示名稱來自第三方地名服務，目前以字串拼接的方式進入頁面標記。改為建立元素並以文字內容的方式寫入名稱，座標則以資料屬性攜帶、由事件處理器讀取，不再拼進行內事件屬性。

### 開發伺服器不同時開啟除錯器與對外綁定

目前啟動方式同時開啟互動式除錯器並綁定所有網路介面，等於把任意程式碼執行的入口開放給同網段。改為關閉除錯器，維持對外綁定不變（手機需要連得到這台機器）。

考慮過的替代方案：保留除錯器但只綁定回環位址。否決的理由是這支工具的使用情境就是從同一台 Mac 的瀏覽器操作連著線的 iPhone，綁定範圍是功能需求，除錯器不是。

## Implementation Contract

**行為**

- 地圖函式庫載入成功且搖桿函式庫載入成功：頁面行為與本變更前完全相同，除了裝置寫入結果三態帶來的初期顯示差異。
- 地圖函式庫載入失敗：地圖區域顯示訊息，內容指出地圖、標記與移動功能不可用；搖桿容器顯示既有的搖桿不可用提示；座標讀數顯示數值、速度標籤顯示數值；搜尋框按 Enter 會送出查詢並列出結果，選取結果只更新座標讀數；設定 GPS 位置、置中標記、開始移動、停止移動、沿路走到這裡五個控制項為停用狀態；主控台有一則具名的錯誤訊息，沒有未捕捉的例外。
- 搖桿函式庫載入失敗而地圖函式庫正常：行為與本變更前相同。
- 兩個函式庫都載入失敗：地圖訊息與搖桿提示同時出現。
- 單點座標寫入失敗：底部狀態列顯示後端回傳的失敗原因；無原因可取時才退回固定文字。
- 自動移動剛啟動、尚無寫入結果：底部狀態列顯示等待裝置回應，狀態圓點未點亮，裝置警示區空白。第一個寫入成功後轉為裝置已連接並點亮圓點；第一個寫入失敗則顯示既有的寫入失敗文字與原因。

**介面與資料形狀**

- 走路狀態查詢端點的回應維持既有欄位名稱。表示裝置寫入結果的欄位其值域由兩個布林值擴充為三種：尚未有結果、成功、失敗；描述失敗原因的欄位在非失敗狀態下為空字串。
- 走路開始端點在回應之前，將裝置寫入結果欄位設為「尚未有結果」，並清空失敗原因欄位。
- 單點寫入端點的回應形狀完全不變。

**失敗模式**

- 函式庫失效一律顯示於頁面上，並在主控台留下一則具名訊息；不得只留主控台訊息。
- 停用的控制項不觸發任何請求，也不產生執行期例外。
- 搜尋服務本身失敗維持現行行為（主控台記錄，不中斷頁面）。

**驗收條件**

- 手動：以瀏覽器開發者工具封鎖地圖函式庫的網址後重新載入頁面，逐條核對上述「地圖函式庫載入失敗」的六項行為。
- 手動：以同樣方式分別封鎖搖桿函式庫、同時封鎖兩者，核對對應的行為。
- 手動：在未連接裝置的情況下按下設定 GPS 位置，確認底部狀態列出現後端回傳的具體原因，而非固定文字。
- 手動：在未連接裝置的情況下啟動多座標移動，確認第一次輪詢顯示等待裝置回應而非裝置已連接，其後轉為寫入失敗與原因。此項若無實體 iOS 裝置無法完成，須明確記錄為未驗證，不得標記為通過。
- 靜態：頁面標記宣告的元素識別字集合，仍為腳本存取的識別字集合的超集。
- 靜態：相依清單中的每一個套件都能在程式碼中找到使用處。

**範圍界線**

- 在範圍內：前端初始化順序與函式庫守衛、地圖不可用時的控制項停用、單點寫入失敗原因的顯示、走路狀態裝置寫入結果的三態、搜尋結果的跳脫、開發伺服器設定、死碼與未使用相依的移除。
- 在範圍外：走路工作執行緒的迴圈與時序（終點寫入、終點進度）、後端對路線與速度的型別驗證、自動化測試框架、文件更新、版本控制的建立。

## Risks / Trade-offs

- 三態的裝置寫入結果讓前端多一條分支 → 前端只在明確成功時點亮，其餘一律視為未確認，分支邏輯保持在單一函式內，不擴散到輪詢迴圈。
- 停用控制項的清單是硬編碼的，日後新增地圖相依控制項時可能忘記加入 → 在停用邏輯處以註解說明這份清單的判準是「是否觸及地圖或標記物件」，讓新增者有判斷依據。
- 無實體裝置時，裝置寫入三態的驗收無法完成 → 依前一次變更的既有慣例，明確記錄為未驗證而非標記通過。
- 關閉除錯器後，開發時的錯誤頁面會變成簡略的錯誤訊息 → 後端錯誤已有主控台輸出，且這支工具的後端邏輯集中在少數幾個函式，影響有限。
- 封鎖 CDN 網址來驗證失敗路徑，模擬的是「載入不到」而非「載入到損壞的版本」 → 後者屬於例外捕捉的範疇，本變更的地圖守衛同時檢查全域物件存在與建立過程不拋錯，兩種情況都會落到同一則訊息。
