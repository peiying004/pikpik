## Context

伺服器與裝置之間有兩層獨立的東西。第一層是 tunneld —— 由啟動腳本以 sudo 執行的獨立程序，維護通往裝置的通道，並在本機 HTTP 端點上列出通道記錄。第二層是伺服器自己持有的共用連線：`_acquire_rsd()` 從 tunneld 取得的 RSD 通道清單中挑出第一筆，`_open_developer_service()` 在其上開啟 Instruments 與定位模擬服務，結果存成 `_dvt` 與 `_location_service` 兩個全域。

RSD 物件在 `connect()` 時會收到裝置的 `peer_info`，其中 `Properties` 帶有 `UniqueDeviceID`、`ProductType`、`OSVersion`。目前這個物件用完即棄，身分資訊沒有任何地方留著。

診斷端點列出的是 tunneld 的通道記錄（udid 與網路介面），那回答的是「tunneld 看得到誰」。連線用的是清單第一筆，兩者在單一裝置時恰好一致。

tunneld 的 HTTP 回應只有 udid、介面名、通道位址、通道埠四個欄位，**沒有機型**。機型只在 RSD 交握之後才存在。但 `_acquire_rsd()` 呼叫的 `get_tunneld_devices()` 會對每一筆通道記錄各做一次交握，回傳的每個物件都帶著 udid、機型代號與 OS 版本，而現行程式只取第一個、其餘全部丟棄——機型其實已經被抓到又扔掉了。

介面名的值形如 `usbmux-<udid>-USB`，因此裝置清單現行的 `udid @ 介面名` 會把同一個 udid 在同一行印兩次，後半沒有增加任何資訊。

tunneld 同時監看 USB 與網路配對兩種來源，因此同一支手機插著線又在同一個區域網路下時會有兩筆通道記錄，兩筆的 udid 相同、介面名不同。通道清單的每一筆各自成為裝置清單的一個項目。

底部狀態列由三處更新：送出座標後（依 `/api/location` 回應的 `device` 欄位）、停止模擬後、以及走路輪詢中（依走路狀態的三態 `device_ok`）。三處各自直接寫入狀態列的文字節點與圓點的樣式類別。沒有任何定期更新，因此頁面閒置時顯示會停在最後一次操作的結果。

伺服器以 Werkzeug 的開發伺服器執行，它為每個請求寫一行存取日誌，格式為請求行、狀態碼、大小三個參數。這個專案的日誌同時承載走路進度與裝置寫入失敗的輸出，那是判斷裝置是否還活著的主要線索。

限制：伺服器以非 sudo 執行且是 tunneld 的子程序，無法啟動或重啟 tunneld。裝置寫入路徑由 `_device_lock` 序列化，任何會建立、替換或關閉共用連線的流程都必須在該鎖之下。

## Goals / Non-Goals

**Goals:**

- 使用者隨時能看出伺服器目前連到哪一台裝置。
- 手機拔掉之後，畫面上的裝置名稱要消失，不能繼續掛著。
- 使用者知道畫面上有一個能主動建立連線的控制項。
- 查詢裝置身分不得對裝置造成任何影響。
- 診斷面板列出的每一台裝置都讀得出是什麼機型，而不是只有一串 udid。
- 定期輪詢不得讓伺服器日誌失去可讀性。

**Non-Goals:**

- 不新增連線端點或第二顆連線按鈕。
- 不提供多裝置選擇，連線沿用通道清單第一筆。
- 不從畫面啟動或重啟 tunneld。
- 不新增靜態 DOM 元素，不新增或修改任何 CSS 規則。
- 不為了取得機型而額外發起任何 RSD 交握或裝置連線。
- 不改變未被選用的 RSD 連線的生命週期。
- 不因日誌量而調整輪詢間隔。
- 不改變身分查詢端點以外任何端點的日誌行為。
- 不改變走路引擎、裝置寫入路徑或既有的三態寫入回報。

## Decisions

### 裝置身分在連線時保留，不從 tunneld 清單推斷

連線成功時把 `_acquire_rsd()` 回傳的 RSD 物件所帶的身分欄位抄存成全域，中斷連線時清除。身分因此來自**實際在用的那條連線**。

考慮過的替代方案：查詢時重新讀一次 tunneld 通道清單，取第一筆當作「在用的裝置」。否決，因為那是在複製 `_acquire_rsd()` 的挑選規則而不是讀取它的結果 —— 兩邊都取第一筆時剛好一致，但那是巧合。清單順序若在兩次查詢之間改變，畫面就會顯示一台伺服器並沒有在用的裝置，而且這種錯沒有任何症狀，使用者要等到定位寫到別支手機上才會發現。

### 回報身分的端點完全不接觸裝置

新端點只做兩件事：讀取記憶體中保留的身分，以及查詢一次 tunneld 的通道清單確認該 udid 是否仍在。不做 RSD 握手、不開開發者服務、不進 `_device_lock`。

這是它與被否決的連線端點之間的關鍵差異，也是它能每 3 秒被呼叫一次的前提。若它會接觸裝置，定期輪詢就會與定位寫入爭搶同一把鎖，並在使用者完全沒有操作時持續對裝置產生流量。

### 區分「伺服器以為連著誰」與「那支手機還在不在」

保留的身分只證明伺服器曾經連上誰，不證明那支手機現在還在。tunneld 的通道清單證明後者。兩者分開回報。

`visible` 採三態而非布林：tunneld 查詢失敗時為未知，不是否。這與專案既有的三態慣例一致（裝置寫入結果的 `device_ok`、診斷階段的未執行狀態）。把「查不到」講成「已離線」會把 tunneld 掛掉的責任推給手機，而使用者接下來要做的事完全不同 —— 一個是重新插上手機，一個是重啟 tunneld。

### 不新增連線端點，改為讓既有的診斷控制項名副其實

診斷端點在共用連線尚未建立時，會走正常連線路徑的同兩個步驟並**保留**結果連線。它已經是一顆主動連線按鈕。

考慮過的替代方案：新增一個只做連線的端點與按鈕。否決 —— 它會是既有連線探測之上的第二層薄殼，藏不住任何行為，只是比診斷少回報三個階段；刪掉它不會有任何東西壞掉。而且連線失敗時它沒有階段資訊可講，使用者還是得再按診斷才知道該修 tunneld 還是開發者模式。真正缺的是標示：控制項沒說它會連線。

### 機型名用函式庫內建對照，不用 RSD 物件的名稱欄位

`ProductType` 是 `iPhone14,2` 這種機型代號。`pymobiledevice3.irecv_devices` 內建代號到可讀名稱的對照，可直接取用，不新增依賴。代號不在對照中時顯示原代號 —— 顯示代號比顯示空白有用。

RSD 物件的名稱欄位**不可使用**：tunneld 的裝置建構流程傳入的是通道記錄的網路介面名，因此該欄位裝的是 `utun4` 這類介面名稱，不是裝置名稱。它看起來像裝置名，是本變更最容易踩中的陷阱。

裝置的使用者自訂名稱（例如「某某的 iPhone」）不在 RSD 交握資訊中，需要 lockdown 才能取得，本變更不為此另開連線。

### 狀態列由單一渲染函式擁有，文字由身分與狀態兩半組成

狀態列目前有三個寫入者各自直接改文字。加入定期輪詢後會出現第四個，四者互相覆蓋：走路中每 500 毫秒寫一次寫入狀態，身分輪詢每 3 秒寫一次裝置名稱，畫面會在兩種文字之間跳動。

改為兩個模組層級變數（裝置標示、裝置狀態）加一個渲染函式：身分輪詢只更新標示，既有三處只更新狀態，兩者都透過渲染函式輸出。文字因此是「裝置名稱 + 狀態詞」的組合，走路中裝置寫入失敗會顯示成 `iPhone 13 Pro 裝置寫入失敗`，兩份資訊同時在場而不是互相取代。

### 輪詢間隔 3 秒

走路輪詢是 500 毫秒，因為它驅動地圖上的標記移動。裝置身分不需要那個頻率：使用者拔掉手機到看見畫面更新之間等 3 秒是可接受的，而每 3 秒一次的本機 HTTP 查詢成本可忽略。輪詢自頁面載入起持續進行，不因走路開始或結束而停止。

### 機型對照取自既有交握的副產品，不另外連線

`get_tunneld_devices()` 已經對每一筆通道記錄各做一次交握，機型代號與 OS 版本就在它回傳的物件上。取得完整清單時把 udid 到機型的對應抄進一個模組層級的字典，再照原樣回傳第一筆。成本是一次字典寫入。

考慮過的替代方案：查詢時對每一台裝置各做一次交握以取得機型。否決——那正是身分查詢端點刻意避開的裝置接觸，而且會把一個唯讀的顯示需求變成會與定位寫入爭鎖的操作。既然資料已經在手上，多連一次沒有任何理由。

對照是顯示輔助，允許過期：只在連線嘗試發生時更新。tunneld 列出一台從未交握過的裝置時，該筆就沒有機型可填，此時欄位缺席而不是填一個猜測值。目前使用中的那一支另有 `_device_identity` 作為來源，即使診斷因沿用既有連線而未重新取得清單，它仍然有名字。

### 使用中標記落在通道記錄上，不是落在裝置上

同一支手機可能同時有 USB 與 Wi-Fi 兩筆通道記錄，udid 相同。以 udid 判斷「使用中」會把兩筆都標上，而實際建立連線的只有被選用的那一條——介面因此在宣稱一件假的事。變更前那兩行只是兩串 udid 與介面名，讀者看得出是同一支手機的兩筆記錄；加上標記之後它才開始說謊，所以這個缺陷是本變更引入的。

判斷所需的欄位已經在手上：通道裝置清單的每個物件建立時，其名稱屬性被填入該筆通道記錄的介面名。把選用物件的介面名連同 udid 一起記進連線身分，使用中就改為比對 udid 與介面名兩者。

有點諷刺：這個名稱屬性正是另一項決策明文禁止當作裝置名稱使用的那一個。它不是裝置名，但它精確地標示了「哪一條通道」，而這裡要的正是後者。

機型名維持以 udid 比對：同一支手機的每一筆記錄都該顯示機型，那是正確的行為，收斂的只有使用中標記。

降級行為明確定義：若身分記錄的介面名不再出現在任何一筆通道記錄中（通道被重建、介面編號改變），則所有記錄的使用中皆為否。寧可一筆都不標，也不要標錯一筆——標錯會讓使用者以為自己在操作另一條通道，而沒有標記只是少一個提示。

### 裝置清單的機型與原始欄位分兩行，沿用既有樣式類別

機型名單獨一行、udid 與介面位址降為次要的一行。原始欄位保留而不刪除——既有需求要求它們被回報，而且拔線前後比對介面位址正是診斷的用途之一。

層次不靠新樣式達成：機型名那一行不加類別，繼承清單容器的一般字級；原始欄位那一行維持既有的等寬小字類別。兩者的既有差異本身就構成主次。刻意不挪用階段狀態的淡化類別——那個類別的語義是「這一階段沒有執行」，用在裝置列上會讓兩種完全不同的狀態共用同一個視覺訊號。

### 可見性只在連線建立與診斷時更新，輪詢不查 tunneld

tunneld 是以 sudo 啟動的獨立程序，基於 FastAPI 與 uvicorn，其根路由就是通道清單。每查一次它就記一行存取日誌，而啟動腳本把它丟在同一個終端機的背景執行——每 3 秒查一次，等於把噪音從這個系統的日誌搬到另一個程序的日誌，而且那個程序的 logger 我們過濾不到。

因此身分查詢端點只讀記憶體。可見性在兩個時刻更新：連線建立時記為「在清單中」（能連上就代表剛才讀到的通道清單裡有它，這個判斷免費且當下為真），以及診斷執行時（診斷本來就會讀通道清單）。

代價是失去「手機被實體拔掉、伺服器卻仍握著連線物件」的自動偵測。這個代價比原本估的小：狀態列大部分的價值來自身分本身，而身分是免費的——停止模擬、連線關閉都會讓身分變 null，狀態列在一個更新週期內就回到「未連接裝置」，不需要任何 tunneld 查詢。真正失去的只有上述那一種，而它另有更權威的來源：實際的裝置寫入。tunneld 的清單只說「通道還在不在」，寫入結果說的是「真的寫得進去嗎」。使用者一動手，第一次寫入失敗就會在狀態列呈現。

考慮過的替代方案：把查詢間隔拉長到 15 或 30 秒。否決——它只是把每小時 1200 行降到 240 或 120 行，噪音的性質不變，而換來的自動偵測在使用者閒置時無人觀看、在使用者動手時又已被寫入結果取代。用不到的東西不值得任何持續成本。

### 輪詢的成功存取日誌被濾掉，失敗仍然記錄

3 秒一次的輪詢每小時產生 1200 行存取日誌。這個專案的日誌要看的是走路進度與裝置寫入失敗，而那些輸出會被輪詢的日誌洗掉 —— 實測時診斷結果就被淹在其中。健康檢查的成功存取日誌沒有診斷價值，濾掉它不損失任何資訊。

**只濾 2xx。** 非 2xx 的回應照常記錄，因為那正是唯一值得看的情形：一個每 3 秒被呼叫的端點若開始回 500，日誌是唯一會說話的地方。把整條路徑一併靜音，會讓這個功能自己的故障變成無聲的。

過濾依 Werkzeug 日誌記錄的參數判斷（請求行與狀態碼），而不是比對格式化後的整行字串。格式化後的訊息在非 2xx 時會被包上終端色碼，以參數判斷不受此影響，也不會因日誌格式改版而失效。

考慮過的替代方案：沒有連線身分時把輪詢間隔退避到 10 秒。否決 —— 那是治標。每小時仍有 360 行，而真正連上裝置後又回到 3 秒，日誌照樣被洗；問題不在頻率，在於健康檢查不該進存取日誌。

## Implementation Contract

**範圍邊界**

- 在範圍內：共用連線建立與中斷時的身分保留、連線嘗試時記錄 udid 到機型的對應、新的唯讀查詢端點、該端點成功回應的存取日誌抑制、診斷回應的裝置項目附帶機型、控制介面的狀態列渲染與定期輪詢、診斷面板裝置清單的兩行呈現、診斷控制項的標示、專案文件的功能涵蓋表與說明。
- 不在範圍內：走路引擎、裝置寫入路徑、`_device_lock` 的使用方式、診斷端點既有的四階段輸出與三態語意、未被選用的 RSD 連線的生命週期、樣式表、控制面板的靜態 HTML 結構。本變更不得新增或移除任何靜態 DOM 元素，不得新增或修改任何 CSS 規則；診斷面板動態產生的裝置列只能沿用既有的樣式類別。

**後端：保留身分**

連線成功後，伺服器持有目前裝置的身分，包含 udid、機型代號、機型可讀名稱、OS 版本，以及該次選用的通道記錄的介面名。中斷連線時該身分被清除。介面名只供判定「哪一筆通道記錄正在使用」，不對外回報。身分在建立與清除時皆處於序列化裝置連線的同一把鎖之下，與既有的連線建立、替換、關閉流程共用互斥範圍。

**後端：查詢端點**

新增一個 GET 端點，回應為 JSON 物件，含兩個鍵：

- `identity`：物件或 `null`。物件含 `udid`、`product_type`、`model`、`os_version` 四個字串欄位。無保留身分時為 `null`。
- `visible`：`true`、`false` 或 `null`，為**最後一次已知**的可見性。`true` 表示最近一次讀到的通道清單中有這個 udid；`false` 表示讀到了清單但其中沒有它；`null` 表示尚未判斷過，或最近一次讀取清單失敗。無保留身分時為 `null`。

該端點**只讀記憶體**：不得建立、替換或關閉任何裝置連線，不得寫入或清除模擬定位，不得改動走路狀態，**也不得查詢 tunneld**。它一律以成功狀態碼回應。

可見性在兩個時刻寫入：共用連線建立時設為 `true`（與身分同時記錄，在同一把裝置鎖之下），共用連線關閉時設為 `null`（與身分同時清除）；以及診斷端點讀取通道清單之後，依清單中是否有目前身分的 udid 設為 `true` 或 `false`，清單讀取失敗時設為 `null`。

**後端：機型對照與診斷裝置項目**

連線嘗試取得通道裝置清單時，伺服器記錄每一台裝置的 udid 到機型代號、機型可讀名稱與 OS 版本的對應。記錄涵蓋清單中的每一台，不只被選用的那一台，且不得為此額外發起任何交握。

診斷回應的裝置清單，每一筆項目除既有的 udid、介面位址、通道位址、通道埠外，在機型已知時另外帶有機型可讀名稱與 OS 版本，並標示該**筆通道記錄**是否為目前使用中的那一條。機型來源依序為：目前連線身分（udid 相符時）、上述對應。兩者皆無時，該筆不帶機型欄位，而不是帶空字串或猜測值。

使用中標記為真的條件是 udid 與介面名**兩者**都與連線身分相符。同一支手機的多筆通道記錄因此至多一筆為真；身分記錄的介面名不在任何一筆記錄中時，全部為否。

身分查詢端點回報的身分物件**不含**介面名：狀態列只需要機型與 OS 版本，介面名對使用者沒有意義，多一個欄位只會擴大契約。

**前端：診斷裝置清單**

裝置清單的每一筆呈現為兩行。第一行是機型可讀名稱與 OS 版本，目前使用中的那一台另加註記；機型未知時第一行省略。第二行是既有的 udid 與介面位址。第一行不套用樣式類別，第二行維持既有的等寬小字類別。

**後端：輪詢的存取日誌**

伺服器啟動時安裝一個存取日誌過濾器。對身分查詢端點的請求，當回應狀態碼為 2xx 時該行不寫入日誌；狀態碼為其他任何值時照常寫入。其他任何路徑的日誌行為不受影響。

判斷依據為日誌記錄所攜帶的請求行與狀態碼參數，不比對格式化後的字串。過濾器不得吞掉走路進度與裝置寫入失敗的輸出，那些不經由存取日誌。

**前端：狀態列**

狀態列文字依身分與狀態組合而成：

| 情境 | 狀態列 | 圓點 |
| ---- | ------ | ---- |
| 無保留身分 | `未連接裝置` | 暗 |
| 有身分，`visible` 為 true | `<機型名> · iOS <版本> 已連接` | 亮 |
| 有身分，`visible` 為 false | `<機型名> 已離線` | 暗 |
| 有身分，`visible` 為 null | `<機型名> · 無法確認狀態` | 暗 |
| 有身分，走路中裝置寫入失敗 | `<機型名> 裝置寫入失敗` | 暗 |

機型代號不在對照表中時，`<機型名>` 為代號本身。

既有的三個狀態列寫入者（送出座標後、停止模擬後、走路輪詢中）改為只更新狀態那一半，不再直接寫入文字節點。身分輪詢只更新身分那一半。兩者都經由同一個渲染函式輸出。

**前端：輪詢**

控制介面自載入起每 3 秒查詢一次該端點。輪詢只使用 DOM 與 fetch，不依賴地圖或搖桿函式庫，因此繫結排在只依賴 DOM 的初始化區塊內，函式庫載入失敗時仍須運作。

**前端：診斷控制項**

診斷控制項的標示須讓使用者在按下之前就知道它會嘗試建立連線。

**失敗模式**

- 端點查詢失敗或回應缺少必要欄位時，該次輪詢保留既有的狀態列文字，不拋出例外中斷輪詢迴圈。
- 伺服器完全無法連上（例如尚未啟動）時，輪詢持續重試，狀態列保留最後一次成功的內容。

**驗收條件**

- 手機連著且已建立連線時，狀態列顯示機型名、iOS 版本與已連接，圓點亮起。
- 拔掉手機後按下診斷，狀態列轉為該機型名加已離線，圓點熄滅；未按診斷前它維持原狀，這是刻意的。
- 停掉 tunneld 後按下診斷，狀態列轉為該機型名加無法確認狀態，而不是已離線。
- 停止模擬後最多一個更新週期內，狀態列回到未連接裝置，且期間未對 tunneld 發出任何請求。
- 連線建立後未執行診斷時，狀態列直接顯示已連接而不是無法確認狀態。
- 身分查詢端點連續呼叫數十次期間，tunneld 的日誌沒有增加任何一行。
- 走路中發生裝置寫入失敗時，狀態列同時呈現機型名與寫入失敗，兩者不互相取代。
- 查詢端點呼叫一百次後，裝置上的模擬定位狀態不變、走路狀態不變、共用連線既未建立也未關閉。
- 機型代號不在對照表中的裝置，狀態列顯示原代號而非空白。
- 診斷控制項的標示提及連線。
- tunneld 列出兩筆通道記錄且兩者都曾交握過時，診斷面板兩筆都顯示機型名，其中一筆標示為使用中。
- 同一支手機同時有 USB 與 Wi-Fi 兩筆通道記錄時，兩筆都顯示機型名，但只有實際連線的那一筆標示為使用中。
- 身分記錄的介面名不在任何一筆通道記錄中時，沒有任何一筆標示為使用中。
- tunneld 列出一台從未交握過的裝置時，該筆只顯示 udid 與介面位址，不顯示機型，也不顯示空白的機型行。
- 診斷面板呈現機型後，樣式表未被修改，控制介面的靜態元素 id 清單與變更前相同。
- 連續呼叫身分查詢端點數十次且皆回應 2xx 後，日誌中沒有任何一行提及該端點。
- 讓身分查詢端點回應非 2xx 時，該行出現在日誌中。
- 呼叫診斷端點與定位端點後，兩者的日誌行照常出現。

## Risks / Trade-offs

- **保留的身分可能與裝置實況不符** → 身分只在連線與中斷時更新，中間不重新確認。`visible` 補上了「手機還在不在」，但無法察覺「同一個 udid 的手機被換成另一台」這種情況。此情境需要每次輪詢都重新交握，代價遠高於價值，不做。
- **多裝置時顯示的是通道清單第一筆** → 把在用的裝置顯示出來，會讓這個任意挑選變得明顯，使用者可能看到不是自己想要的那支卻無法更換。這是刻意的取捨：顯示與選擇是兩件事，本變更只做前者。
- **每 3 秒一次的輪詢在頁面閒置時仍持續** → 該端點不接觸裝置，成本是一次本機 HTTP 查詢與一次字典查找。停掉輪詢會讓狀態列重新變回會過期的欄位，那正是本變更要消除的問題。
- **介面名可能在通道重建後改變** → 那會讓使用中標記在下一次診斷時消失，直到重新建立連線。這是刻意選擇的降級方向：沒有標記只是少一個提示，標錯則會讓使用者以為自己在操作另一條通道。
- **機型對照可能過期** → 它只在連線嘗試時更新。一台曾經交握過、之後換上另一個 udid 的裝置不會造成錯誤（udid 是對應的鍵），但一台從未交握過的裝置就沒有名字。此時欄位缺席而非填猜測值——顯示 udid 比顯示一個可能錯的機型名好。
- **未被選用的 RSD 連線仍然沒有被關閉** → `get_tunneld_devices()` 為每一筆通道記錄開啟連線，現行程式只保留第一個。本變更多讀取這些物件已經帶回來的欄位，不改變其生命週期，因此既不加重也不減輕這個既有問題。刻意不順手修：那是連線生命週期的變更，會動到裝置路徑，與本變更的顯示目的無關。
- **可見性會過期** → 手機被實體拔掉而使用者閒置時，狀態列會繼續顯示已連接，直到執行診斷或發生一次裝置寫入。這是刻意接受的：閒置時沒有人依賴它做決定，而一旦動手，寫入結果會立刻糾正，且寫入結果比通道清單更權威。
- **靜音一條路徑就是放棄它的存取日誌** → 只濾 2xx 把代價縮到最小：成功的健康檢查沒有資訊，失敗的仍然看得見。但若該端點開始回應 2xx 卻內容錯誤（例如永遠回傳空身分），日誌不會提示，只有畫面會。這是可接受的：畫面本來就是這個功能的輸出所在。
- **狀態列由四個來源共同組成** → 改為單一渲染函式後，任何新的寫入者都必須經過它。直接寫入文字節點的程式碼會再次造成互相覆蓋，而這種錯只在特定時序下出現。
