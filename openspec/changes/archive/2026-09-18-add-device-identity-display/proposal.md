## Why

底部狀態列只說「裝置已連接」，從不說是**哪一支**。連線建立時，`_acquire_rsd()` 取得的 RSD 物件帶著 udid、機型代號與 OS 版本，但這些資訊在 `_open_developer_service()` 之後就被丟棄 —— 只有 `_dvt` 與 `_location_service` 被保留下來。

診斷面板列出的裝置清單也答不了這個問題：那是「tunneld 看得到誰」，而連線用的是 `devices[0]`。一支手機時兩者恰好一致，但那是巧合而非保證，而這種不一致沒有任何症狀。

狀態列還有一個既有缺口：它只在送座標、停止模擬、或走路輪詢時更新。頁面開著不操作，顯示會停在最後一次操作的結果。若在這樣的欄位上加裝置名稱，手機拔掉之後名稱會繼續掛著 —— 比不顯示更糟。

另一半的需求其實已經存在但沒人知道：診斷控制項會建立連線並**刻意保留**它（`connection-diagnostics` 的 `Diagnostics reuses the existing device connection`），等同於一顆主動連線按鈕，只是名字沒說。

## What Changes

- 連線時保留 `_acquire_rsd()` 取得的 RSD 物件，中斷連線時清除。裝置身分來自實際在用的那條連線，不是 tunneld 清單的第一筆。
- 新增唯讀端點回報伺服器目前對裝置的認知：保留的身分（機型名、OS 版本、udid），以及該裝置**最後一次已知**的可見性。此端點**只讀記憶體** —— 不做 RSD 握手、不開開發者服務、不進裝置鎖，也不查詢 tunneld。可見性在連線建立時記為「在清單中」（能連上就表示剛才讀到的清單裡有它），之後由診斷更新。
- 前端每 3 秒輪詢該端點並更新底部狀態列。狀態列因此能區分三件事：連著誰、連過但已離線、從未連線。
- 機型代號經 `pymobiledevice3.irecv_devices` 內建的對照轉成可讀機型名（例如 `iPhone14,2` → `iPhone 13 Pro`），查不到時顯示原代號。**不使用 RSD 物件的 name 屬性** —— 那個欄位裝的是網路介面名（`utun4` 之類），不是裝置名稱。
- 診斷控制項更名為「連線並診斷」，讓它既有的連線行為在按下去之前就看得出來。
- 診斷面板的裝置清單為**每一筆**通道記錄顯示機型名，不只是目前使用中的那一支；而「使用中」標記只落在**實際建立連線的那一筆通道記錄**上。同一支手機同時插線又在同一個 Wi-Fi 下時，tunneld 會回報兩筆 udid 相同的記錄，若只比對 udid 就會把兩筆都標成使用中 —— 其中一筆是假的。機型名不需要任何額外連線：`_acquire_rsd()` 呼叫的 `get_tunneld_devices()` 本來就對每一筆記錄各做一次交握，回傳的物件都帶著機型代號與 OS 版本，現行程式只取第一個、其餘全部丟棄。留下 udid 到機型的對應是零成本。
- 裝置清單每一筆改為兩行：機型名一行，原本的 udid 與介面位址降為次要的小字一行。現在那一行是 `udid @ interface`，而介面位址的值是 `usbmux-<udid>-USB`，同一個 udid 在同一行印了兩次。
- 可見性**不定期查詢 tunneld**。tunneld 是 sudo 起的獨立程序（FastAPI + uvicorn），它的根路由就是通道清單，每查一次它就記一行 —— 而啟動腳本把它丟在同一個終端機的背景。每 3 秒查一次等於把噪音搬到另一個程序，我們還無法過濾它的日誌。改為只在連線建立與執行診斷時更新。
- 身分查詢端點的**成功**存取日誌不再寫入伺服器日誌。3 秒一次的輪詢每小時產生 1200 行，把這個專案日誌真正要看的東西（走路進度、裝置寫入失敗）洗掉 —— 實測時診斷結果就被淹在其中。**非 2xx 的回應仍然記錄**：把失敗一起藏起來，等於藏掉唯一值得看的那一筆。

## Non-Goals

- **不新增連線端點或第二顆連線按鈕。** 主動連線的能力已存在於診斷路徑中，新端點會是既有連線探測之上的第二層薄殼：它藏不住任何行為、只是少回報三個階段，刪掉它什麼都不會壞。而且連線失敗時它沒有階段資訊可講，使用者仍得再按診斷才知道是 tunneld 沒開還是開發者模式沒打開。
- **不提供多裝置選擇。** 連線沿用 `devices[0]`，只把在用的那一支顯示出來。顯示與選擇是兩件事，後者工作量差一截。
- **不從畫面啟動 tunneld。** tunneld 由啟動腳本以 sudo 執行，而伺服器是它的非 sudo 子程序，無法在不要密碼、不殺掉自己父程序的前提下重啟它。畫面上的控制項只能涵蓋通道連線與開發者服務兩個階段。
- **不新增靜態 DOM 元素，也不新增或修改任何 CSS 規則。** 狀態列沿用既有的文字節點與狀態圓點。診斷面板的裝置清單本來就是每次診斷動態產生的，新增的機型名那一行沿用既有的樣式類別：機型名不加類別（繼承清單容器的一般字），原始欄位維持既有的等寬小字類別，層次由兩者的既有差異形成。
- **不為了取得機型而額外發起任何 RSD 交握或裝置連線。** 只使用既有連線流程本來就會做的那些握手。做不到就讓該筆不帶機型，而不是多連一次。
- **不修正未被選用的 RSD 連線沒有被關閉這件事。** `get_tunneld_devices()` 會為每一筆通道記錄開啟連線，而現行程式只保留第一個、其餘既不使用也不關閉。這是既有行為，本變更只是多讀取它們已經帶回來的欄位，不改變其生命週期。
- **不改變走路引擎、裝置寫入路徑或既有的三態寫入回報。**
- **不因日誌量而降低輪詢頻率。** 問題不在請求頻率而在於一個健康檢查不該進存取日誌 —— 退避到 10 秒每小時仍有 360 行，而真正連上裝置後又回到 3 秒，日誌照樣被洗；那是治標。
- **不自動偵測「手機被實體拔掉但伺服器仍握著連線物件」。** 那是唯一需要定期查詢 tunneld 才能察覺的情況，而它另有更權威且免費的來源：實際的裝置寫入。使用者一動手，第一次寫入失敗就會在狀態列呈現。閒置時名稱可能過期，但閒置時它也騙不到人。
- **不改變其他端點的日誌行為。** 只有身分查詢端點的成功回應被濾掉，`/api/location`、`/api/diagnostics`、走路端點一律照舊。

## Capabilities

### New Capabilities

- `device-identity`: 伺服器目前連到哪一台裝置，以及該裝置是否仍可見。涵蓋連線時保留裝置身分、以不接觸裝置的方式回報該身分、機型代號到可讀名稱的轉換，以及狀態列對「連著誰／已離線／從未連線」三種狀態的呈現。

### Modified Capabilities

- `connection-diagnostics`: 兩條需求要改。其一，診斷控制項的需求目前只規定它呈現階段結果，未提及它同時會建立並保留連線，新增規定：該控制項的標示須讓使用者在按下之前就知道它會嘗試建立連線。其二，裝置記錄的需求目前要求每筆項目的欄位「原樣取自 tunneld」，而機型名不是 tunneld 給的、是交握後推導的，需明確允許這個衍生欄位，並規定無從得知時該欄位缺席而非臆測。

- `project-documentation`: 功能涵蓋表新增本次功能與其錨點詞，以滿足「新增功能時須於同一個變更中加入涵蓋表」的既有需求。
