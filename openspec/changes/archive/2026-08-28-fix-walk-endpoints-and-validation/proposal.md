## Problem

多座標依序移動有四個彼此獨立、都落在走路工作執行緒的迴圈與輸入邊界上的缺陷：

1. **路線的第一個座標從來沒有送到裝置。** 走路以第一個座標為起點，但在派送任何寫入之前就先前進了一個週期的距離。18 km/h 下那是一公尺，速度愈高偏差愈大。`auto-walk` 明文要求「the device location is set to the first coordinate」，並以 25.033964,121.564468 為範例值，目前不成立。

2. **路線的最後一個座標可能永遠沒有送到裝置。** 抵達終點那一個週期若正好有前一次寫入尚未完成，本次寫入會依既有的丟棄策略被跳過；而迴圈條件在同一刻不再成立，沒有任何補寫機會。使用者看到介面顯示已抵達終點，裝置卻停在終點前的某個位置。

3. **終點的進度幾乎永遠顯示不出來。** 後端把進度寫成最後一個索引的同一瞬間就把移動中狀態設為否，前端每 500 毫秒才輪詢一次、而且只在移動中才更新進度顯示，所以「第 3 點／共 3 點」落在一個極窄的時間窗內。`auto-walk` 明文要求進度在抵達第三個座標後讀作 coordinate 3 of 3。

4. **陳舊的寫入完成回呼會污染新一輪走路的裝置寫入狀態。** 完成回呼不帶任何識別，無法分辨自己屬於哪一輪走路；停止走路只等待工作執行緒結束，不等待也不取消已派送的寫入協程。上一輪的寫入若在新一輪開始之後才完成，它的結果會覆寫新一輪剛重設的「尚未有結果」。

另有一個獨立於上述四項的輸入邊界問題：**走路開始端點不驗證路線與速度的型別。** 目前只有狀態欄位取用了轉型後的第一個座標，交給工作執行緒的是原封不動的輸入。座標若為字串，距離計算會拋出型別錯誤、工作執行緒當場結束、移動中狀態被收尾邏輯設為否；前端第一次輪詢讀到未移動便送出停止請求，使用者看到的正是「按下開始卻馬上停下」——而 `auto-walk` 有一整條要求就是為了防止這個症狀。

## Root Cause

前三項的共同根源是**走路迴圈把「推進位置」與「把位置送到裝置」綁在同一個週期節奏上，而沒有為路線的起點與終點保留獨立的處理**。迴圈的不變式是「每個週期先前進、再視情況寫入」，這個不變式在路線中段是對的，在兩個端點都不成立：起點不需要先前進，終點之後沒有下一個週期可以補救。進度顯示是同一個問題的前端投影——終點狀態存在的時間短於輪詢週期。

第四項的根源是**寫入的完成回呼與走路的生命週期沒有關聯**。回呼直接寫入共用的走路狀態字典，而那個字典會被下一輪走路重設；兩者之間沒有任何序號或代次可以讓回呼判斷自己是否已經過期。

輸入驗證問題的根源是**驗證只做在回應路徑上，沒有做在交給工作執行緒的資料上**。狀態欄位取用了轉型後的值，讓錯誤型別在回應階段看起來無害，實際的失敗被推遲到背景執行緒，且以一個與成因完全無關的症狀呈現。

## Proposed Solution

- **起點寫入**：走路開始移動之前，先把路線的第一個座標派送一次裝置寫入，再進入推進迴圈。
- **終點寫入**：迴圈結束後，若最後一個座標尚未成功送達，補派送一次寫入，且這一次不套用「前一次尚未完成就丟棄」的規則。
- **終點進度**：把自然走完與使用者按停止兩種收尾區分開來。自然走完時，前端在清理路線之前先讓進度顯示停在最後一個座標的索引；使用者按停止時維持現行的清除行為。
- **回呼代次**：為每一輪走路配一個遞增的代次編號，寫入派送時帶上該編號，完成回呼只在編號與當前輪次相符時才寫入走路狀態，否則整筆結果丟棄。
- **輸入驗證**：走路開始端點在啟動工作執行緒之前，把路線的每一組座標轉為數值並檢查緯度與經度的範圍，把速度轉為數值並檢查為正；任一項不成立就以四百級別的錯誤回應拒絕，不啟動任何工作執行緒。

## Non-Goals

- **不改動「重疊的寫入直接丟棄而非排隊」這條既有規則本身。** 起點與終點的寫入是這條規則的兩個明確例外，中段的行為完全不變。丟棄策略解決的是裝置位置落後於顯示位置的問題，把它換成排隊會讓那個問題回來。
- **不縮短前端的輪詢週期。** 用更密的輪詢去撞終點那個時間窗只是把機率從低變成較低，沒有消除競態。
- **不處理停止走路時工作執行緒的加入逾時。** 停止走路等待工作執行緒最多兩秒，理論上逾時後可能有兩個工作執行緒並存。工作執行緒的等待上限是一個週期的兩百毫秒，實際觸發需要極端的排程延遲，且與本變更的四項缺陷沒有共用的修改面。
- **不為走路加入自動化測試框架。** 專案目前沒有測試基礎建設，本變更沿用前一個變更的作法：以 Flask 測試客戶端搭配替換掉的裝置寫入函式驗證後端，以無頭瀏覽器驗證前端。
- **不改動走路狀態端點既有的欄位名稱。**

## Success Criteria

- 走路開始後，裝置收到的第一個座標與路線的第一個座標完全相同。
- 走路自然結束後，裝置收到的最後一個座標與路線的最後一個座標完全相同，即使抵達終點那一刻正好有寫入尚未完成。
- 三個座標的走路自然結束後，進度顯示讀作第三個座標，且在路線清理之前對使用者可見。
- 上一輪走路的寫入在新一輪開始之後才完成時，新一輪的裝置寫入結果維持在「尚未有結果」。
- 路線含有非數值座標、或速度為非數值或非正值時，走路開始端點以四百級別的錯誤回應拒絕，不啟動工作執行緒，且走路狀態維持未移動。
