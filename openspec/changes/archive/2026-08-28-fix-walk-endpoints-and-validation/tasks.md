## 1. 後端：路線起點與終點的裝置寫入

- [x] 1.1 依「起點與終點的寫入是丟棄策略的兩個具名例外」決策，讓走路在進入推進迴圈之前先派送一次路線第一個座標的裝置寫入，且該次派送不受「前一次尚未完成就丟棄」規則限制。完成後可觀察到 `Multi-waypoint sequential walk` 的「First coordinate reaches the device before any interpolation」情境：裝置收到的第一個座標與路線第一個座標完全相同，之前沒有任何插值位置。驗證：以 Flask 測試客戶端啟動走路，並把裝置寫入函式替換為記錄呼叫座標的樁，斷言樁收到的第一組座標等於路線第一組座標。
- [x] 1.2 依「起點與終點的寫入是丟棄策略的兩個具名例外」決策，讓走路在推進迴圈自然結束後，若路線最後一個座標尚未送達就補派送一次寫入，判斷依據為「最後成功送達的座標是否等於路線終點」而非「是否為最後一個週期」，且該次派送同樣不受丟棄規則限制。完成後可觀察到 `Multi-waypoint sequential walk` 的「Final coordinate reaches the device even when a write was in flight」情境。驗證：以刻意變慢的裝置寫入樁製造抵達終點時仍有寫入未完成的情況，斷言樁最終收到的座標等於路線最後一組座標。
- [x] 1.3 核對 `Overlapping walk writes are dropped rather than queued` 修改後的完整要求：兩個端點的寫入是例外、其餘週期的丟棄行為完全不變、使用者停止時不派送終點寫入。完成後可觀察到該要求範例表五列的行為。驗證：以裝置寫入樁記錄每一次派送，分別在自然走完與中途停止兩種情況下比對樁收到的座標序列，逐列核對範例表。

## 2. 後端：寫入完成回呼的代次辨識

- [x] 2.1 依「完成回呼以代次編號辨識自己屬於哪一輪走路」決策，為每一輪走路配一個單調遞增的代次編號並於走路開始端點重設狀態時遞增；派送寫入時帶上當時的代次，完成回呼先比對代次，不相符就整筆丟棄，不寫入走路狀態、不記錄失敗、不改動進行中旗標。代次編號不出現在任何回應中。完成後可觀察到 `Write outcomes from a superseded walk are discarded` 的三個情境。驗證：以 Flask 測試客戶端搭配刻意變慢的裝置寫入樁，在上一輪派送寫入後立刻啟動新一輪，斷言舊寫入完成之後新一輪的裝置寫入結果仍為尚未有結果、失敗原因仍為空字串。
- [x] 2.2 確認代次機制沒有壓抑當前輪次自己的寫入結果：當前輪次的寫入完成後，成功與失敗都仍然照常反映到走路狀態。驗證：以會成功的樁與會拋錯的樁各跑一輪走路，斷言走路狀態分別轉為成功與失敗並帶出原因；並以命令列查詢走路狀態端點的回應，確認不含任何代次欄位。

## 3. 後端：走路開始端點的輸入驗證

## 驗證註記

驗證於 2026-08-28 執行。後端以 Flask 測試客戶端跑 app.py 的真實程式碼，只把唯一與裝置通訊的入口 `_set_location` 換成可控延遲與可控失敗的樁；前端以無頭 Chrome 151 搭配注入頁面的診斷探針。本變更的斷言 74 項全數通過，另重跑前一個變更留下的 140 項斷言全部仍然通過。

**已驗證（以裝置寫入樁，非實機）**

- 起點寫入：第一次派送的座標等於路線第一個座標，之前沒有任何插值位置。
- 終點寫入：以 0.5 秒延遲的樁製造「抵達終點時仍有寫入未完成」，補寫仍然發生，裝置最終收到的座標等於路線終點。
- 丟棄規則的五列例外表逐列核對，包含以直接呼叫派送函式驗證「進行中旗標為真時，中段寫入被丟棄、端點寫入仍派送、且端點派送不會誤放掉別人持有的旗標」。
- 使用者按下停止時，路線終點從未被派送，裝置停在停止當下的位置。
- 代次辨識的四種時序：舊寫入先完成而新一輪自己尚未完成、舊寫入以失敗完成而新一輪已成功、舊寫入以成功完成而新一輪已失敗、以及當前輪次自己的成功與失敗照常套用。
- 走路狀態端點的回應仍是原本的八個欄位，不含任何代次欄位（以命令列對實際 HTTP 端點查詢，該查詢為純讀取，未觸發任何裝置寫入）。
- 輸入驗證的八列範例表逐列核對，另確認被拒絕的請求不會把正在進行的走路停掉，且交給工作執行緒的是轉型後的浮點數而非原始字串。
- 前端收尾分流：自然走完後進度顯示為第 3 點／共 3 點並在標記與折線移除之後仍可見；使用者按下停止則進度與路線一併清除。
- 三座標路線跑完一次完整走路，進度索引依序經過 0、1、2，走路自然結束。

**未驗證**

- **實體 iOS 裝置的寫入未驗證。** 所有裝置寫入在測試中都被替換為樁，沒有任何一次寫入真的送到裝置。執行當下有連著的實體裝置與運作中的 tunneld，但依使用者在前一個變更中的決定，不對實機進行測試。
- 連帶未驗證的是：起點與終點的兩次寫入在真實裝置上的送達與時序；終點補寫與前一次寫入在真實裝置連線上排隊時的實際行為（設計上由 `_device_lock` 與寫入逾時保護，未在硬體上觀察）。

補作方式：在連著裝置且 tunneld 運作時，以三個相距數公尺的座標啟動一次多座標移動，走完後確認裝置的定位停在路線的最後一個座標而非其前方；再以同一段路線在中途按下停止，確認裝置停在按下當時的位置而非被推到終點。
