## Context

專案是一套在 macOS 上執行的 iOS 定位注入工具。Flask 伺服器已綁定所有網路介面
(host 為 0.0.0.0),行走引擎跑在後端執行緒而非瀏覽器,因此手機端網頁進入背景或鎖屏
時移動不會中斷。這兩項既有性質使「以 iPhone 遙控自身定位」在傳輸與執行層面已經成立。

剩下的落差有兩處。其一,樣式表沒有任何視窗寬度斷點,面板為固定 250px 絕對定位浮層、
搖桿固定 140×140 貼右下,窄螢幕上兩者重疊。其二,裝置連線鏈的失敗全部收斂成單一
訊息;函式庫在把 tunneld 通道轉為可用裝置時會靜默跳過連線逾時並回傳空清單,使得
成因不同、處置不同的三種狀況在介面上無法區分。

安裝與環境層面另有前提條件(裝置須已與 Mac 配對、開發者模式開啟、Wi-Fi 同步啟用),
這些不在程式可控範圍內,但診斷應當讓使用者看出是哪一段不成立。

## Goals / Non-Goals

**Goals:**

- 讓裝置連線鏈的四個階段各自回報成敗與可執行的後續動作,取代單一籠統訊息。
- 在窄視窗下提供可用的觸控版面,面板與搖桿不重疊。
- 讓頁面可加入 iOS 主畫面並以獨立全螢幕模式啟動。
- 回報可從手機存取的伺服器網址,免去手動查詢 Mac 位址。
- 不新增任何 Python 或前端執行期依賴。

**Non-Goals:**

- **不實作暫停後繼續移動。** 使用者明確排除。既有的停止語意不變,`_walk_state` 不新增欄位。
- **不自動判定通道走 USB 或 Wi-Fi。** tunneld 的回應只含通道位址與介面位址,沒有連線型態欄位;
  由位址型態推測不可靠。改為原樣顯示介面位址,由使用者自行比對拔線前後的差異。
- **不做原生 iOS App。** 外殼內仍是同一個網頁,卻要付出憑證與定期重簽的成本,換不到新能力。
- **不做桌面打包。** 現有的啟動腳本已完成同樣的工作,外殼不含任何它沒有的行為。
- **不修改裝置寫入路徑。** 持久連線、重疊寫入的丟棄規則、代次辨識與三態回報皆不變動。
- **不修正啟動腳本殘留 tunneld 的問題。** 該問題確實存在(終止訊號送往 sudo 程序而非其子程序),
  但與手機遙控無關,屬另一個變更。
- **不代理第三方服務。** 圖磚、地點搜尋與路徑規劃仍由瀏覽器直連。

## Decisions

### 診斷以標準程式庫查詢 tunneld,不觸碰函式庫私有函式

tunneld 在 127.0.0.1 的固定通訊埠上提供 HTTP 端點,回應為以 UDID 為鍵、通道記錄陣列為值的
JSON 物件。函式庫內部以一個底線開頭的私有函式取得這份清單。診斷改以標準程式庫的 urllib
直接查詢該端點,位址取自函式庫已公開的 TUNNELD_DEFAULT_ADDRESS 常數。

替代方案是引入該私有函式,或加入 requests 套件。前者會讓診斷綁在函式庫的未公開介面上,
函式庫升版即可能無聲失效;後者雖然 requests 已被 pymobiledevice3 間接安裝,但把它寫進
直接依賴會擴大依賴面。urllib 在標準程式庫中且足以完成一次 GET 與 JSON 解析。

### 診斷分四個階段,每階段回報可執行的後續動作

四個階段依序為:tunneld 是否可達、是否發現裝置、通道能否連上、開發者服務能否開啟。
每個階段獨立回報成敗;任一階段失敗即停止後續階段並指出後續動作,因為後續階段的前提已不成立。

階段之所以停在「開發者服務能否開啟」而不含「寫入座標」,見下一項決策。

替代方案是保留單一布林結果並補上文字說明。但成因與處置的對應關係是分階段的——
「tunneld 沒啟動」要重啟服務、「未發現裝置」要接線或檢查配對、「通道連不上」要重啟 tunneld、
「開發者服務開不起來」要檢查開發者模式。把四者壓成一則訊息正是目前的缺陷。

### 診斷不得有副作用,並重用既有的裝置連線

診斷不寫入座標、不清除模擬定位、不關閉既有連線。

第三與第四階段涉及實際連線,處理方式為:若共用的定位服務已建立,兩階段直接回報成功並跳過探測——
既有連線能存在本身就證明通道與開發者服務可用。若尚未建立,則沿用既有的連線建立路徑,
並在同一把裝置鎖的保護下進行,連線建立後保留而不關閉(等同為後續操作暖機)。

替代方案是每次診斷都自行建立一條獨立的通道連線再關閉。但同一裝置上並存兩條連線可能互相干擾,
且關閉時有機會連帶影響共用連線。重用既有路徑與既有鎖,可讓診斷不引入任何新的並行狀況。

### 回報可從手機存取的伺服器網址

診斷回應中包含伺服器的區網位址與通訊埠,使使用者不必自行查詢 Mac 的 IP 即可在手機上輸入。
位址取得方式為開啟一個 UDP socket 並指定一個外部目標,再讀取本端位址;此操作不送出任何封包。

已知限制:只能取得預設路由所對應的那一個位址,不列舉所有網路介面。當 Mac 同時連著多個網路
時,回報的位址可能不是使用者預期的那一個。列舉全部介面需要第三方套件,與不新增依賴的目標衝突,
因此接受此限制並在介面上將其標示為「預設路由位址」而非唯一位址。

### 窄視窗將面板改為底部抽屜並縮小搖桿

以視窗寬度 768 CSS 像素為斷點。寬視窗維持現狀,窄視窗改為:面板貼齊視窗底部、寬度佔滿、
預設收起僅顯示標題列,展開時高度上限為視窗高度的一半並內部捲動;搖桿縮小並上移至面板之上,
與面板不重疊。

觸控目標的最小尺寸取 44 CSS 像素,此為 Apple 人機介面指南對觸控目標的建議下限,
也是一個可直接量測的驗收數值。既有的按鈕最小高度為 52px 已達標,滑桿與收起控制項需要檢查。

替代方案是讓面板在窄視窗維持左側浮層但縮減寬度。但面板有四個區段、含一個多行座標輸入框,
壓縮寬度後仍會佔據畫面主要部分並蓋住地圖;而地圖正是選定目的地所必需的操作對象。
底部抽屜讓地圖保有上半部的完整可視區域。

### 主畫面圖示以 Python 標準程式庫產生

iOS 主畫面圖示須為 PNG,不接受 SVG。以一支獨立指令稿用標準程式庫的 zlib 與 struct
產生兩個純色圓角圖示檔(180 像素供 iOS 主畫面,512 像素供資訊清單參照),不引入影像處理套件。

替代方案是完全不提供圖示——iOS 會改用網頁截圖作為圖示。可行但辨識度差,且與資訊清單所宣告的
圖示不一致。另一替代方案是加入 Pillow,但為兩個純色圖示引入影像處理套件不成比例。

### 診斷面板的初始化歸入僅依賴文件的階段

診斷面板不依賴地圖或搖桿函式庫,其標記建立與事件繫結須排在任何第三方函式庫初始化之前,
與既有的座標讀數、速度標籤同一階段。這使得任一函式庫載入失敗時診斷仍然可用——
而函式庫失敗恰好是使用者需要診斷的時機之一。

## Implementation Contract

**Behavior**

使用者在控制面板中觸發診斷後,看到四個階段各自的成敗、成功階段的細節、失敗階段的原因與
後續動作,以及可從手機存取的伺服器網址。診斷不改變裝置的模擬定位狀態。

在寬度不超過 768 CSS 像素的視窗中,控制面板位於視窗底部、預設收起,搖桿不與面板重疊,
地圖上半部完整可見。頁面可經 iOS Safari 的分享選單加入主畫面,並以無網址列的獨立模式啟動。

**Interface / data shape**

新增一個唯讀的診斷端點,以 GET 方法回應 JSON。回應包含:

- 一個階段陣列,元素依序對應 tunneld 可達性、裝置發現、通道連線、開發者服務,
  每個元素含階段識別字、階段顯示名稱、三態結果(成功、失敗、因前置階段失敗而未執行)、
  細節文字、後續動作文字。
- 一個裝置陣列,每個元素含 UDID、介面位址、通道位址與通道通訊埠;無裝置時為空陣列。
- 伺服器位址欄位,含預設路由位址與通訊埠。

三態結果不得以布林表示——「未執行」與「失敗」是不同的狀況,理由與既有裝置寫入結果採三態相同。

新增一份 Web 應用程式資訊清單,宣告應用名稱、獨立顯示模式、起始網址、背景與主題色,
以及所產生的 512 像素圖示。頁面 head 另需 iOS 專用的主畫面圖示與獨立模式參照。

**Failure modes**

- tunneld 未啟動:第一階段失敗,細節指出無法連上 tunneld 的位址,後續動作指出需啟動 tunneld;
  其餘三階段回報為未執行。
- 未發現裝置:第二階段失敗,後續動作指出需接線,或檢查裝置是否已與此 Mac 配對信任、
  是否啟用 Wi-Fi 同步、是否開啟開發者模式。
- 通道連線逾時:第三階段失敗,細節帶通道位址,後續動作指出需重啟 tunneld。
- 開發者服務開啟失敗:第四階段失敗,細節帶所捕捉的錯誤說明。
- 診斷端點自身不得因任何階段失敗而回應非 2xx 狀態碼。階段失敗是診斷的正常輸出,
  不是端點的錯誤;以非 2xx 回應會讓前端無法區分「診斷跑完且發現問題」與「診斷本身壞了」。
- 取得伺服器位址失敗時,該欄位回報為空字串而非使整個診斷失敗。

**Acceptance criteria**

- 在 tunneld 未啟動的狀態下呼叫診斷端點,回應狀態碼為 2xx,第一階段為失敗,其餘三階段為未執行。
- 在裝置已連線且可用的狀態下呼叫診斷端點,四個階段皆為成功,裝置陣列含至少一個元素且帶 UDID。
- 連續呼叫診斷端點兩次,再讀取行走狀態端點,行走狀態不因診斷而改變。
- 診斷前後,裝置上的模擬定位位置不變。
- 於寬度 375 CSS 像素的視窗檢視頁面,面板與搖桿的邊界框不相交。
- 於寬度 375 CSS 像素的視窗檢視頁面,面板預設為收起且其標題列可見。
- 頁面所宣告的元素識別字集合仍涵蓋頁面指令稿所存取的全部識別字。
- 資訊清單可經伺服器取得且為合法 JSON,其所參照的圖示檔存在且可取得。
- 停用地圖函式庫的載入後,診斷面板仍可觸發並回報結果。

**Scope boundaries**

在範圍內:診斷端點與其面板、窄視窗版面規則、觸控尺寸調整、資訊清單與圖示、
以及上述兩份既有規格中與視窗寬度相關的要求鬆綁。

在範圍外:暫停後繼續移動、啟動腳本的 tunneld 殘留問題、裝置寫入路徑的任何變動、
連線型態的自動判定、多網路介面的列舉、原生 App 與桌面打包。

## Risks / Trade-offs

- **診斷的第四階段會建立並保留裝置連線** → 這與既有的第一次設定位置行為相同,
  且受同一把裝置鎖保護,不引入新的並行狀況。若使用者只想查看狀態卻意外建立了連線,
  影響僅是連線提早建立,不改變裝置的模擬定位。
- **伺服器位址只回報預設路由對應的那一個** → 於介面上標示其為預設路由位址,
  不宣稱為唯一可用位址。多網路情境下使用者仍可自行查詢。
- **無法自動判定通道走 USB 或 Wi-Fi** → 原樣顯示介面位址,並在面板上說明可比對拔線前後的差異。
- **窄視窗改為底部抽屜會與既有規格的「面板位於左側」衝突** → 已將該要求鬆綁為僅適用於寬視窗,
  並以差異規格記錄,而非在實作中默默違背規格。
- **手動產生的 PNG 圖示若格式有誤,iOS 會靜默改用網頁截圖** → 驗收條件要求圖示檔可經伺服器取得;
  格式錯誤時 iOS 的退化行為不會導致頁面失效,僅圖示外觀不如預期。
- **診斷面板增加了面板的內容高度** → 窄視窗的展開高度上限為視窗高度一半且內部捲動,
  既有規格對面板不得溢出視窗的要求仍然適用。
