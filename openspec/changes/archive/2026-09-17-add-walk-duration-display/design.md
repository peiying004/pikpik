## Context

走路引擎以固定速度在相鄰座標之間直線插值前進（後端 `_walk_worker`，每 200 毫秒推進一次，每次推進 `speed_kmh * 1000 / 3600 * 0.2` 公尺）。不繞路、不等紅燈、不重新規劃，因此「還要走多久」是剩餘距離除以速度的算術結果，不是需要統計或猜測的估計值。

走路狀態查詢端點已經回傳目前位置、已抵達座標的索引（0 起算）、座標總數，以及**這一輪走路實際採用的速度**。前端在送出走路請求時也保留了自己的路線陣列：多座標依序移動存在 `multiCoords`，單點沿路存在 `routeCoords`。計算所需的輸入已經全部到齊。

顯示元素也已經存在：控制面板中負責進度的那個元素，目前只在多座標依序移動進行中被寫入「第 N 點／共 M 點」。它的樣式是小字等寬綠字。

限制：控制面板寬 250 像素；進度元素字級 11 像素。自動移動速度滑桿的範圍是 5 到 40 km/h，後端另外驗證速度必須大於 0。

## Goals / Non-Goals

**Goals:**

- 使用者在按下開始移動之前，就能看到多座標路線的全長與所需時間。
- 兩條走路路徑（多座標依序移動、單點沿路）進行中都能看到剩餘時間。
- 顯示的數字等於走路引擎真的要做的事，而不是別的系統對同一條路線的看法。
- 後端零改動。

**Non-Goals:**

- 不在放置或拖曳綠色目的地標記時預覽單點沿路的時間，不為此額外呼叫外部路線規劃服務。
- 不使用外部路線規劃服務回應中現成的距離與時間欄位。
- 不在後端計算，不擴充走路狀態查詢的回應欄位。
- 不新增 DOM 元素，不重新配置控制面板，不調整既有樣式。
- 不改變走路引擎、裝置寫入或任何後端行為。
- 不補償走路迴圈的實際落後（見風險）。

## Decisions

### 時間在前端計算，後端契約不變

走路是固定速度的純插值，後端與前端算出的是同一個數字，準確度不構成選邊的理由。真正的分水嶺是「開始之前」的預估在後端根本不存在 —— 那時還沒有走路，沒有狀態可查。把計算放前端，一套函式同時涵蓋開始前與進行中兩個時機，且不需要新增任何 API 欄位。

考慮過的替代方案：在走路狀態中新增剩餘距離與剩餘秒數欄位。否決，因為它只能服務「進行中」這一半，開始前的預估仍得在前端另外實作一次，等於同一套幾何運算寫兩遍；而且它擴大了走路狀態查詢的契約，卻換不到任何準確度。

此專案只有單一前端頁面，手機遙控是同一頁的窄視窗版面，因此「多個客戶端需要共用計算結果」這個通常支持後端的理由在這裡不成立。

### 移動中的速度取自走路狀態，不取自滑桿

速度在走路開始請求被處理的當下就凍結進走路狀態，之後拖動滑桿不會影響正在跑的那一輪走路。因此進行中的剩餘時間必須用走路狀態回傳的速度，開始前的預覽才用滑桿的目前值。

用滑桿值計算進行中的剩餘時間會產生最難察覺的一種錯：使用者拖動滑桿，畫面上的倒數立刻改變，裝置卻仍以原速前進。顯示與現實脫節，而且沒有任何錯誤訊息。

### 距離自行以 haversine 累加，不用路線規劃服務的現成欄位

外部路線規劃服務的回應帶有距離與時間兩個欄位，但兩個都不能用：時間是開車時間，距離是路網長度。走路引擎拿到座標後，是在相鄰座標之間**直線插值**前進的。自行以 haversine 累加相鄰座標的距離，顯示的數字才保證等於走路引擎真的要做的事。

副作用是兩條走路路徑共用同一個距離函式，只有一種行為要驗證。

### 單點沿路只有移動中倒數，沒有開始前預覽

單點沿路的路線是按下按鈕之後才向外部服務取得的，取得後立刻送出走路請求，中間沒有可以插入預覽的時刻。要造出這個時刻有兩種做法，都被否決：在標記落點變動時先打一次路線規劃服務（每次拖曳標記都是一次外部請求，而目前的設計刻意只在使用者按下按鈕時呼叫一次）；或把操作拆成「先看路線與時間、再按確認」兩步（多一次點擊，改掉一個目前很順的流程）。

倒數的第一個值本來就等於這條路線的總時間，資訊沒有少，只是晚 500 毫秒出現。而且停止鍵就在旁邊，按下去之後發現太久就停掉，代價近乎零。

### 沿用既有進度元素，不新增 DOM

進度元素雖然位在「多座標依序移動」區段，控制面板早就把該區當成共用的走路狀態區：裝置警示元素緊接在它下方，而更新裝置警示的呼叫在每次輪詢都執行、不分走路種類；停止移動按鈕反過來住在「單點沿路」區段，卻同時被多座標依序移動使用。單點沿路的剩餘時間顯示在該元素中，不會建立新的違例。

### 時間與距離的格式

距離：未滿 1000 公尺以整數公尺顯示（`784 公尺`），1000 公尺以上以公里顯示到小數點後一位（`5.7 公里`）。

時間：先把秒數四捨五入為整數秒，再依量級選格式。未滿 1 分鐘顯示「45 秒」；未滿 1 小時顯示「18 分 55 秒」，餘數為 0 秒時省略秒（「18 分」）；1 小時以上顯示「1 小時 5 分」，捨去秒 —— 在小時的量級上標出秒是假精確。

開始前的預覽加「約」（`全長 5.7 公里 · 約 18 分 55 秒`），進行中的倒數不加（`第 2 點／共 3 點 · 剩餘 12 分 58 秒`）。兩者都是近似值，但「約」的用途是提醒使用者不要拿它去規劃分秒必爭的事，而一個每 500 毫秒跳動一次的倒數本身就已經表明了它的性質，再加「約」只是雜訊。

### 走完之後不保留剩餘時間

多座標依序移動自然走完時，既有邏輯會把最後一次讀到的進度文字保留在元素中。保留的文字只含座標索引，不含時間 ——「剩餘 0 秒」沒有資訊量。

使用者按下停止時，以及單點沿路的任何收尾，維持現況整行清空。

## Implementation Contract

**範圍邊界**

- 在範圍內：控制介面頁面的前端腳本（新增六個函式與三個呼叫點）、專案文件的功能涵蓋表與對應說明。
- 不在範圍內：後端任何檔案、樣式表、走路引擎、裝置寫入、控制面板的 HTML 結構。本變更不得新增或移除任何 DOM 元素，不得新增或修改任何 CSS 規則。

**新增函式**

| 函式 | 輸入 | 輸出 |
| ---- | ---- | ---- |
| `haversineMeters(lat1, lng1, lat2, lng2)` | 兩組十進位度數座標 | 兩點間大圓距離，單位公尺 |
| `routeLengthMeters(coords)` | `[[lat, lng], ...]` | 相鄰座標距離總和，單位公尺；少於兩點時為 0 |
| `remainingMeters(coords, reachedIndex, lat, lng)` | 路線陣列、已抵達座標索引（0 起算）、目前位置 | 目前位置到 `coords[reachedIndex + 1]` 的距離，加上其後所有線段長度；`reachedIndex` 已指向最後一點時為 0 |
| `formatDistance(meters)` | 公尺 | 依上述格式規則產生的距離字串 |
| `formatDuration(seconds)` | 秒 | 依上述格式規則產生的時間字串 |
| `updateRoutePreview()` | 無 | 無回傳；重算並寫入開始前的預覽文字 |

`haversineMeters` 是後端 `_haversine` 的 JavaScript 對應，使用相同的地球半徑 6371000 公尺與相同公式。

**呼叫點**

- 座標輸入元素新增輸入事件處理，呼叫 `updateRoutePreview()`。該元素目前沒有任何事件處理。
- 更新自動移動速度的既有函式（速度滑桿的輸入事件入口，同時也是頁面初始化時推導速度標籤與速度變數的地方）在其原有工作之後呼叫 `updateRoutePreview()`。
- 走路輪詢的既有函式在每次成功讀到走路狀態且走路仍在進行時，重算剩餘時間並寫入進度元素。

**可觀察行為**

- 多座標依序移動未開始時，座標輸入有效且達兩點以上，進度元素顯示 `全長 <距離> · 約 <時間>`。長度由 `routeLengthMeters` 作用在**當下解析座標輸入所得的陣列**上求得，時間為該長度除以滑桿目前速度。不讀 `multiCoords`：那個變數要到走路開始時才被填值，開始前恆為空陣列。
- 座標輸入無效、座標少於兩點、或輸入為空時，預覽文字清空。座標解析失敗時不得沿用上一次有效輸入的預覽 —— 顯示與輸入框內容不符的路線長度，比不顯示更糟。
- 多座標依序移動進行中，進度元素顯示 `第 <N> 點／共 <M> 點 · 剩餘 <時間>`。時間由 `remainingMeters(multiCoords, 進度索引, 狀態位置)` 除以**走路狀態回傳的速度**求得。
- 單點沿路進行中，進度元素顯示 `剩餘 <時間>`，無座標索引前綴。路線陣列用 `routeCoords`，速度同樣取自走路狀態。
- 多座標依序移動自然走完後，進度元素保留 `第 <M> 點／共 <M> 點`，不含時間。
- 使用者按下停止移動後，進度元素清空。單點沿路無論自然走完或被停止，進度元素皆清空。

**失敗模式**

- 路線陣列為空或走路狀態缺少必要欄位時，該次輪詢不寫入時間，保留既有文字，不拋出例外中斷輪詢。輪詢迴圈的既有錯誤處理不得因本變更而失效。
- 速度為 0 或負值在此不需處理：滑桿下限為 5，後端拒絕不大於 0 的速度。

**驗收條件**

以規格中的範例路線手動驗證（`25.033964,121.564468` → `25.041000,121.565000` → `25.047924,121.517081`，兩段分別 784 公尺與 4888 公尺，全長 5673 公尺）：

- 貼入該三行座標、速度滑桿在 18，預覽顯示 `全長 5.7 公里 · 約 18 分 55 秒`。
- 滑桿拉到 36 而不改動座標，預覽即時變為 `全長 5.7 公里 · 約 9 分 27 秒`。
- 開始移動，進度元素在第一次輪詢後轉為 `第 1 點／共 3 點 · 剩餘 <時間>`，其時間隨輪詢遞減。
- 移動中拖動速度滑桿，進行中的剩餘時間**不因此改變**（僅未開始時的預覽會變）。
- 走完後進度元素停在 `第 3 點／共 3 點`，不帶時間。
- 放置綠色目的地標記並按下沿路走到這裡，進度元素顯示 `剩餘 <時間>` 且不含座標索引；按下停止移動後清空。
- 將第三行改為 `25.047924, abc`，預覽清空且不殘留前一次的長度。

## Risks / Trade-offs

- **走路迴圈在機器忙碌時會落後標稱速度** → 迴圈每個週期睡「固定間隔減去本週期已耗用時間」，週期超時就無法補回，因此實際耗時可能略長於計算值。以「約」與整秒四捨五入表達近似性質，不做落後補償 —— 補償需要量測實際推進速率並回報到前端，那正是本設計刻意避開的後端契約擴張，而誤差量級（正常負載下遠小於 1%）不值得。
- **進度文字加長後可能在 250 像素寬的面板中換到第二行** → 不設定不換行、不縮小字級，讓它自然換行。強制單行會把文字擠出面板邊界，縮字級則動到既有樣式而本變更明確不改樣式。
- **單點沿路的路線可能有上千個座標點，每 500 毫秒重算一次剩餘距離** → 每次重算是一趟線性掃描，數千點的量級在毫秒以下，遠小於 500 毫秒的輪詢間隔。若日後路線規模成長到造成卡頓，可在走路開始時預先算好線段長度的後綴和；現在不做，因為那是為了不存在的問題增加狀態。
- **預覽文字與進行中文字之間有最長 500 毫秒的空窗** → 按下開始移動後、第一次輪詢回來之前，元素仍顯示預覽文字。兩者對同一條路線給出一致的時間，不會閃出錯誤資訊，因此不額外處理。
