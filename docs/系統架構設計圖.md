# iOS GPS 模擬器 — 系統架構設計圖

本文件說明「iOS GPS 模擬器」的整體系統架構、模組分層、資料流向與部署方式。
所有圖表以 [Mermaid](https://mermaid.js.org/) 語法撰寫，可在支援 Mermaid 的 Markdown 檢視器（GitHub、VS Code + 外掛、Typora 等）中直接渲染。

---

## 1. 系統概觀

本專案是一套執行於 **macOS** 的工具，透過網頁地圖介面，將指定的經緯度座標「模擬」注入到已連線的 **iOS 裝置**，使裝置回報虛擬的 GPS 位置。除了單點定位外，還支援搖桿即時移動與沿真實道路自動行走。

| 項目 | 內容 |
|------|------|
| 執行平台 | macOS（需 Python 3.13+） |
| 後端框架 | Flask（Python） |
| 前端 | 單頁 HTML + Leaflet 地圖 + nipplejs 搖桿 |
| 裝置通訊 | pymobiledevice3（DVT / Instruments 通道） |
| 對外服務 | OpenStreetMap 圖磚、Nominatim 地點搜尋、OSRM 路徑規劃 |
| 服務埠 | HTTP `8080` |

## 4. 單點定位資料流（設定 GPS 位置）

```mermaid
sequenceDiagram
    participant U as 使用者
    participant FE as 前端 (index.html)
    participant BE as Flask (app.py)
    participant BG as 背景 event loop
    participant DEV as iOS 裝置

    U->>FE: 拖曳標記 / 搜尋 / 點「設定 GPS 位置」
    FE->>BE: POST /api/location {lat, lng}
    BE->>BE: 轉型 float、加鎖更新 current_location
    BE->>BG: _run_async(_set_location)
    alt 尚未連線
        BG->>DEV: _connect() 建立 DvtProvider + LocationSimulation
    end
    BG->>DEV: location_service.set(lat, lng)
    alt 連線失效
        BG->>DEV: _disconnect() → _connect() → 重試 set()
    end
    BG-->>BE: 完成
    BE-->>FE: {status: ok, device: true/false}
    FE->>U: 更新狀態燈（已連接 / 未連接）
```

## 5. 自動沿路行走資料流

本章涵蓋兩條自動移動路徑。兩者只在「送出走路開始請求之後」合流：後端的推進、寫入與收尾邏輯完全相同，差別全在前段如何取得座標。

### 5.1 單點沿路移動

由外部路線規劃服務取得道路座標，座標會被吸附到道路上。

```mermaid
sequenceDiagram
    participant U as 使用者
    participant FE as 前端
    participant OSRM as OSRM 路徑服務
    participant BE as Flask
    participant W as _walk_worker 執行緒
    participant DEV as iOS 裝置

    U->>FE: 點地圖放目的地 → 按「沿路走到這裡」
    FE->>OSRM: GET 路線 (起點→終點)
    OSRM-->>FE: 道路座標陣列 (GeoJSON)
    FE->>FE: 於地圖繪製路線 polyline
    FE->>BE: POST /api/walk/start {route, speed_kmh}
    BE->>BE: _parse_walk_request 驗證座標與速度
    BE->>BE: 代次遞增、寫入結果重設為「尚未有結果」
    BE->>W: 建立背景執行緒
    W->>DEV: 起點寫入（路線第一個座標，不受丟棄規則限制）
    loop 每 200ms tick
        W->>W: 依速度 + _haversine 計算下一點
        W->>BE: 更新 _walk_state
        alt 前一次寫入已完成
            W->>DEV: 派送寫入（帶當時代次）
            DEV-->>W: _on_walk_write_done：代次相符才記錄成功或失敗
        else 前一次寫入尚未完成
            W->>W: 丟棄本次寫入（不計為失敗）
        end
    end
    W->>DEV: 終點補寫（自然走完且終點尚未送達時）
    loop 每 500ms（與上方迴圈並行）
        FE->>BE: GET /api/walk/status
        BE-->>FE: {active, lat, lng, progress, total, device_ok, device_error}
        FE->>FE: 移動標記、地圖跟隨、呈現裝置寫入結果三態
    end
    opt 使用者中途停止
        U->>FE: 按「停止移動」
        FE->>BE: POST /api/walk/stop
        BE->>W: 設定停止事件 → join；不補寫終點
    end
```


### 5.2 多座標依序移動

座標由使用者逐行輸入，不經過任何外部服務，也不吸附道路——落點就是輸入的座標。

```mermaid
sequenceDiagram
    participant U as 使用者
    participant FE as 前端
    participant BE as Flask
    participant W as _walk_worker 執行緒
    participant DEV as iOS 裝置

    U->>FE: 於控制面板逐行輸入座標 → 按「開始移動」
    FE->>FE: parseCoordInput 解析並驗證，錯誤時回報輸入行號
    FE->>FE: 繪製編號標記與折線，地圖視野涵蓋所有座標
    FE->>BE: POST /api/walk/start {route, speed_kmh}
    BE->>BE: _parse_walk_request 驗證座標型別與經緯度範圍、速度為正
    alt 驗證失敗
        BE-->>FE: 4xx + error 說明
        FE->>FE: 於面板顯示原因，不啟動移動
    else 驗證通過
        BE->>BE: 代次遞增、寫入結果重設為「尚未有結果」
        BE->>W: 建立背景執行緒
        W->>DEV: 起點寫入（路線第一個座標，不受丟棄規則限制）
        loop 每 200ms tick
            W->>W: 依速度插值推進，更新 _walk_state
            W->>DEV: 寫入目前座標；前一次尚未完成則丟棄本次
        end
        W->>DEV: 終點補寫（自然走完且終點尚未送達時）
        loop 每 500ms（與上方迴圈並行）
            FE->>BE: GET /api/walk/status
            BE-->>FE: {active, lat, lng, progress, total, device_ok, device_error}
            FE->>FE: 移動標記、顯示「第 N 點／共 M 點」與裝置寫入狀態
        end
    end
    opt 使用者中途停止
        U->>FE: 按「停止移動」
        FE->>BE: POST /api/walk/stop
        BE->>W: 設定停止事件 → join；不補寫終點
    end
```

與 5.1 的差異：**沒有外部路線規劃服務參與**，且多了前端的座標解析與後端的輸入驗證兩道關卡。

## 6. 連線狀態機（iOS 定位服務）

```mermaid
stateDiagram-v2
    [*] --> 未連線
    未連線 --> 連線中: 首次 set / walk
    連線中 --> 已連線: DvtProvider + LocationSimulation 建立成功
    已連線 --> 已連線: set(lat, lng) 成功
    已連線 --> 重連中: set() 拋出例外 (通道失效)
    重連中 --> 已連線: _disconnect → _connect → 重試成功
    重連中 --> 未連線: 重試失敗
    已連線 --> 未連線: /api/stop → _clear_location
    未連線 --> [*]
```

## 8. 關鍵設計決策

| 決策 | 原因 |
|------|------|
| 專屬背景 event loop 執行緒 | Flask 為同步框架，pymobiledevice3 為 async；以獨立 loop 承載非同步呼叫並保持長連線，避免每次請求重建成本。 |
| 持久化 DVT 連線（全域 `_dvt` / `_location_service`） | 連線建立成本高，重複使用可讓即時搖桿與自動行走達到低延遲更新。 |
| set() 失敗自動重連一次 | iOS 通道可能因閒置或裝置狀態而失效，單次重連提升穩定性。 |
| 自動行走放在後端執行緒 | 位置需以固定節奏（200ms）持續注入，交由後端可不受瀏覽器分頁節流影響；前端僅輪詢顯示。 |
| 前端直連第三方服務 | 圖磚、地點搜尋、路徑規劃皆由瀏覽器直接請求，後端無須代理，降低伺服器負載。 |
| 重疊的裝置寫入直接丟棄，不排隊 | 移動期間每個週期都會派送一次寫入。若改成排隊，慢速裝置會讓待寫入無上界累積，裝置位置離顯示位置愈來愈遠。丟棄較舊的座標不損失資訊——較新的座標已包含它。丟棄不計為失敗、不回報為錯誤。 |
| 路線起點與終點是丟棄規則的兩個具名例外 | 推進迴圈的不變式是「先前進、再視情況寫入」，這在路線中段成立，在兩個端點都不成立：起點不該先前進，終點之後沒有下一個週期可補救。兩者以不受丟棄限制的方式派送；終點補寫只在自然走完時進行，使用者按停止時不補。 |
| 寫入完成回呼以代次辨識所屬輪次 | 停止走路只等待工作執行緒結束，不等也不取消已派送的寫入協程。上一輪的結果若在新一輪開始後才回來，會覆寫新一輪剛重設的狀態。每輪配一個遞增代次，回呼比對不符就整筆丟棄。取消協程無法保證及時生效，代次比對則行為確定。 |
| 裝置寫入結果採三態而非布林 | 走路剛開始時第一次寫入的結果還沒回來。若預設為成功，前端第一次輪詢就會在毫無根據下宣稱裝置已連接。以「尚未有結果／成功／失敗」表達，前端只在明確成功時才點亮狀態。 |
| 第三方函式庫載入失敗必須在頁面上看得見 | 函式庫失效曾讓半個頁面靜默失效，使用者只看到彼此無關的症狀。每個函式庫各自判定可用性，任一個的失敗不遮蔽另一個的回報；失效時在該控制項的位置顯示不可用訊息，並停用會用到它的控制項。 |
| 走路輸入驗證前置於啟動工作執行緒 | 型別錯誤若留到背景執行緒才爆開，走路狀態已設為移動中、回應也送出了，使用者看到的是「按下開始卻馬上停下」，與成因毫無關聯。驗證提前到回應之前，且排在停止前一輪走路之前——被拒絕的請求不得動到任何走路狀態。 |
