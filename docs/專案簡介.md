# iOS GPS 模擬器 — 專案簡介

一套在 macOS 上執行的定位注入工具。透過網頁地圖選定座標，經由 DVT／Instruments
通道寫入已連線的 iOS 裝置，讓裝置回報虛擬的 GPS 位置。

| 項目 | 數值 |
|------|------|
| 後端 | `app.py` — 708 行 |
| 前端 | `templates/index.html` — 876 行 |
| 樣式 | `static/css/style.css` — 528 行 |
| 圖示產生 | `tools/make_icons.py` — 92 行 |
| API 端點 | 8 個 |
| 裝置寫入週期 | 200 ms |
| 規格驗收情境 | 127 個 |

---

## 1. 專案簡介與動機

開發與測試具備定位功能的 iOS App 時，最麻煩的一件事是「你必須真的走到那裡」。
地理圍欄的進出、路線追蹤的連續性、跨區域的行為差異——這些都無法在辦公桌前重現。
Xcode 內建的模擬位置只能餵固定座標或預錄的 GPX，不能即時操控，也無法在真機上邊看邊調。

這個專案要解決的就是這件事：**把 iOS 裝置的定位變成一個可以即時操控的東西**。
打開瀏覽器、在地圖上點一下，裝置就在那裡；推動搖桿，裝置就跟著移動；框一條路線，
裝置就以指定時速沿路走完。

三種操作模式對應三種測試情境：

- **單點定位** — 驗證靜態位置下的行為
- **搖桿即時移動** — 驗證連續位置追蹤
- **自動沿路行走** — 驗證長時間的軌跡記錄

控制介面本身就在瀏覽器裡，而伺服器綁定所有網路介面，所以**同一支被注入定位的
iPhone 可以同時當遙控器**：手機開啟同網段的網址即可操作，不必回到電腦前。行走引擎
跑在後端執行緒而不是瀏覽器，因此手機鎖屏或切換到其他 App 時移動不會中斷。頁面可經
Safari 的分享選單加入主畫面，以 `manifest.webmanifest` 宣告的獨立模式啟動，看起來
與一般 App 無異；窄視窗下控制面板改為貼底的抽屜、觸控目標放大到 44 CSS 像素 的下限。

裝置端不需要越獄，也不需要安裝任何東西，全部透過 Apple 官方的 Instruments
開發者通道完成。

## 2. 使用技術

| 分類 | 內容 |
|------|------|
| **後端** | Python 3.13、Flask 3.0+。同步 HTTP 框架，搭配一條專屬的背景 `asyncio` event loop 執行緒承載非同步的裝置通訊。 |
| **裝置通訊** | pymobiledevice3 4.0+。經 `tunneld` 建立 RSD 通道，透過 `DvtProvider` 取得 Instruments 通訊能力，再以 `LocationSimulation` 服務寫入座標。 |
| **前端** | 原生 JavaScript 單頁，無框架、無建置工具。Leaflet 1.9 負責地圖與標記，nipplejs 0.10 提供虛擬搖桿。 |
| **外部服務** | OpenStreetMap 圖磚、Nominatim 地點搜尋、OSRM 路徑規劃。三者皆由瀏覽器直接請求，後端不代理。 |
| **連線診斷** | 以標準程式庫的 `urllib` 查詢 tunneld 的 HTTP 端點，位址取自函式庫公開的 `TUNNELD_DEFAULT_ADDRESS`；本機位址以 `_default_route_address` 取得。不新增任何依賴。 |
| **加入主畫面** | `manifest.webmanifest` 宣告獨立顯示模式，`tools/make_icons.py` 以標準程式庫的 `zlib` 與 `struct` 產生 PNG 圖示。 |
| **併發模型** | `threading` 承載行走引擎與 event loop，`asyncio.Lock` 序列化裝置寫入，`run_coroutine_threadsafe` 跨越同步與非同步的邊界。 |
| **開發流程** | 規格驅動開發（SDD）。9 份能力規格、52 條需求、127 個驗收情境，每次變更留下提案、設計與任務紀錄。 |

## 3. 系統架構與亮點

整體是一條從瀏覽器到 iOS 裝置的單向寫入鏈。關鍵在於中間那一層——Flask 是同步的，
pymobiledevice3 是非同步的，而裝置連線的建立成本很高，不能每次請求都重建。

```
┌──────────────────────────────────────────┐
│ 瀏覽器                                    │
│ index.html · Leaflet · nipplejs          │
└──────────────────────────────────────────┘
   │                    ╎
   │ HTTP :8080         ╎ 直連，不經後端
   │                    └╌╌▶ OSM 圖磚
   │                        Nominatim 搜尋
   │                        OSRM 路徑規劃
   ▼
┌──────────────────────────────────────────┐
│ Flask 應用                                │
│ app.py · 8 endpoints · 行走引擎           │
└──────────────────────────────────────────┘
   │ run_coroutine_threadsafe
   ▼
┌──────────────────────────────────────────┐
│ 背景 event loop 執行緒                    │
│ asyncio · _device_lock 序列化             │
└──────────────────────────────────────────┘
   │ DVT / Instruments
   ▼
┌──────────────────────────────────────────┐
│ iOS 裝置                                  │
│ LocationSimulation.set(lat, lng)         │
└──────────────────────────────────────────┘
```

### 五個設計上的取捨

**持久連線，而非每次重建**

DVT 通道的建立成本高。全域保留 `_dvt` 與 `_location_service`，由一條專屬的背景
event loop 執行緒承載，讓搖桿的即時移動能達到低延遲更新。寫入失敗時自動重連一次
——iOS 通道會因閒置或裝置狀態失效，單次重連涵蓋絕大多數情況。

**行走引擎放在後端，不放前端**

位置必須以固定的 200ms 節奏持續注入。放在瀏覽器會受分頁節流影響——切到背景分頁，
計時器就被降頻，軌跡立刻失真。改由後端執行緒推進，前端只負責每 500ms 輪詢顯示。

**重疊寫入直接丟棄，不排隊**

座標以每週期約一公尺推進，較新的座標已經包含較舊座標的資訊。若改成排隊，慢速裝置
會讓待寫入無上界累積，裝置位置離顯示位置愈來愈遠。丟棄不計為失敗、不回報為錯誤
——但路線的起點與終點是這條規則僅有的兩個具名例外。

**函式庫失效必須看得見**

每個第三方函式庫各自獨立判定可用性，任一個的失敗不遮蔽另一個的回報。失效時在該
控制項的位置顯示不可用訊息，並停用所有會用到它的按鈕，而不是讓一次頂層中斷散成
一連串執行期的空值存取。

**診斷分階段回報，而且不留副作用**

`/api/diagnostics` 把連線鏈拆成四個依序探測的階段，每個階段各自回報成敗與該做的下一步。
任一階段失敗就停止後續階段，並把它們標為未執行——「前面就斷了所以沒跑」和「跑了而且
失敗」要做的事不一樣，用布林表達會把兩者混為一談。整個端點是唯讀的：不寫入座標、
不清除模擬定位、不關閉既有連線。涉及實際連線的兩個階段沿用共用連線而非另開一條，
同一裝置上並存兩條通道連線會互相干擾。

## 4. 克服的挑戰

以下五個問題有一個共通點：**使用者看到的症狀，和真正的成因毫無關聯**。
這也是它們難找的原因。

### 4.1 停止再開始後，裝置狀態被上一輪的結果覆寫〔競態條件〕

- **症狀** — 停止行走後立刻重新開始，新一輪的裝置狀態偶爾顯示為上一輪的失敗訊息。難以穩定重現。
- **成因** — 停止行走只等待工作執行緒結束，**不等也不取消已派送的寫入協程**。上一輪的寫入可能在新一輪開始之後才完成，其回呼會覆寫新一輪剛重設的狀態。
- **解法** — 為每輪行走配一個遞增的**代次編號**，派送時一併帶入回呼。回呼比對代次，不符就整筆丟棄。選擇代次而非取消協程，是因為取消無法保證及時生效，代次比對則行為確定。

### 4.2 裝置還沒回應，介面卻已宣稱連接成功〔狀態建模〕

- **症狀** — 按下開始行走，狀態圓點立刻亮起「裝置已連接」，即使裝置根本沒接上。
- **成因** — 裝置寫入結果用布林值表示，預設為 `True`。行走剛開始時第一次寫入的結果還沒回來，前端第一次輪詢就在毫無根據的情況下讀到了成功。
- **解法** — 改為**三態**：`None` 表示這一輪還沒有任何寫入結果、`True` 成功、`False` 失敗。前端只在明確讀到成功時才點亮圓點，第三態顯示「等待裝置回應」。

### 4.3 一個 404 讓三個無關的功能同時失效〔失效隔離〕

- **症狀** — 速度標籤空白、座標讀數留在佔位符號、搜尋框 Enter 鍵完全沒反應。三個看似無關的症狀，同時出現。
- **成因** — 搖桿函式庫 nipplejs 載入失敗（404）。而**頂層敘述拋錯會中斷其後所有頂層敘述**——那三項初始化剛好都排在腳本最後面，於是一起沒執行。它們其實完全不需要搖桿。
- **解法** — 把**只依賴 DOM 的初始化前置**到任何函式庫初始化之前，並讓每個函式庫各自獨立判定可用性（以 `typeof` 判斷，對未宣告識別字安全）。這條順序關係後來被寫成規格的四條需求、九個驗收情境。

### 4.4 按下開始，卻馬上自己停下〔驗證時機〕

- **症狀** — 送出座標後行走立刻中止，介面回到未移動狀態，沒有任何錯誤訊息。
- **成因** — 座標若是字串，距離計算會在**背景執行緒**拋出型別錯誤。執行緒當場結束、收尾邏輯把移動中狀態設為否，而此時 HTTP 回應早已送出。前端第一次輪詢讀到未移動，於是送出停止請求。
- **解法** — 把驗證**完整前置到回應之前**，並排在「停止前一輪行走」之前——被拒絕的請求不得動到任何行走狀態。逐點檢查型別、有限性與經緯度範圍，錯誤訊息帶上是第幾個座標點。

### 4.5 介面顯示已抵達終點，裝置卻停在前一個位置〔邊界條件〕

- **症狀** — 行走完成後，裝置回報的位置與路線終點差了幾公尺。速度愈快，差距愈大。
- **成因** — 「前一次寫入未完成就丟棄本次」這條規則，在路線中段是對的，在兩個端點都不成立：**起點**不該先前進一個週期才寫入，**終點**被丟棄後已經沒有下一個週期可以補救。
- **解法** — 起點與終點以不受丟棄限制的方式派送，成為這條規則僅有的兩個**具名例外**。終點的判斷依據是「最後成功送達的座標是否等於路線終點」，而非「這是不是最後一個週期」——因為迴圈也可能被使用者提早停止，而那時**不該**把裝置推到終點。
