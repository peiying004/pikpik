## 一、後端 `app.py`

後端是一個 Flask 應用，負責提供 API、管理與 iOS 裝置的持久連線，並在背景執行自動行走運算。

### 1. 全域狀態與連線物件

**連線與座標**

- `current_location`：目前模擬的座標，供前端查詢與自動行走共用。
- `lock`：保護 `/api/location` 對座標的更新，避免多請求競態。
- `_dvt` / `_location_service`：**持久化**的裝置連線物件（`DvtProvider` 與 `LocationSimulation`），全程重複使用以降低延遲。
- `_loop` / `_loop_thread`：承載 asyncio event loop 的背景執行緒。

**裝置寫入的保護機制**

- `_device_lock`：非同步互斥鎖，序列化所有會建立、替換或關閉共用連線的流程。移動期間每個週期都會派送一次寫入，沒有它，多個協程會同時進入重連分支並互相關閉對方剛建好的連線。
- `_DEVICE_WRITE_TIMEOUT`：單次裝置寫入的秒數上限。超時視為寫入失敗，讓下一個週期能重新嘗試，避免一個永不完成的寫入把後續寫入永久卡住。

**走路狀態**

- `_walk_state`：移動中旗標、目前座標、進度索引、總點數、裝置寫入結果與失敗原因，由前端每 500ms 輪詢讀取。
- `_walk_write_inflight`：移動期間是否已有一個裝置寫入尚未完成。由移動執行緒設為真、由完成回呼清除，是「重疊寫入直接丟棄」的判斷依據。
- `_walk_last_sent`：最後一次**成功完成**的寫入所帶的座標。終點補寫用它判斷路線的最後一個座標是否已經真的送達，而不是去猜哪一個週期是最後一個。
- `_walk_generation`：走路的代次編號，每次走路開始時遞增。用來辨識一筆寫入結果屬於哪一輪走路。

### 2. 非同步事件迴圈橋接

Flask 為同步框架，而 `pymobiledevice3` 使用 `async`。這裡以一條專屬背景執行緒承載 event loop，將 async 呼叫橋接成同步結果。

`_ensure_loop()` 確保有一條在背景執行緒運行的 asyncio event loop（已在運行就直接返回）；`_run_async(coro)` 把協程排到那條 loop 上並等待結果。

**重點**：`_run_async` 是同步 API 路由呼叫 async 裝置操作的統一入口，會等待結果，逾時上限由 `_DEVICE_WRITE_TIMEOUT` 定義。

自動行走走的是另一條路徑：以 `run_coroutine_threadsafe` 派送寫入後**不等待結果，但掛上完成回呼**（`_on_walk_write_done`）。回呼會取出協程的結果，成功與失敗都記錄到 `_walk_state`——這不是射完就不管的作法，未取用的例外會被 Future 吞掉，裝置早已凍結時介面仍會顯示一切正常。

---

### 3. iOS 定位服務連線管理

連線需分兩層建立：先 `DvtProvider`（提供 Instruments 通訊能力），再 `LocationSimulation`。

`_connect()` 依序建立兩層：先透過 `tunneld` 取得裝置的 RSD 連線並建立 `DvtProvider`（提供 Instruments 通訊能力），再把它交給 `LocationSimulation`。找不到裝置時拋出說明 tunneld 未啟動的錯誤。

`_disconnect()` 以**相反順序**關閉：先定位服務、再 DVT，確保資源正確釋放。

- 透過 `tunneld` 取得裝置的 RSD（Remote Service Discovery）連線。
- 關閉時**順序相反**，確保資源正確釋放。

---

### 4. 座標注入與清除

`_set_location(lat, lng)` 是**唯一**把座標送到裝置的入口，所有路徑（單點寫入、搖桿移動、自動行走）都經過它。行為分三段：

1. 取得 `_device_lock`。整段（含重連）都在鎖內，因此任一時刻只有一個協程能建立、替換或關閉共用的連線物件。
2. 連線不存在就先建立。
3. 呼叫定位服務寫入座標；若拋錯，視為通道失效，關閉後重連一次再重試一次。

`_clear_location()` 取消裝置上的模擬定位並關閉連線，同樣在 `_device_lock` 內完成。

**為什麼必須互斥**：移動期間每個週期都會派送一個定位寫入協程。若不互斥，多個協程會同時進入重連分支，互相關閉對方剛建好的連線——症狀是連線反覆斷開、寫入持續失敗，而且看起來像裝置問題。

**容錯設計**：`set()` 失敗會自動重連一次再重試，提升長時間使用的穩定性；單次寫入另有 `_DEVICE_WRITE_TIMEOUT` 的時間上限，避免一個永不完成的寫入卡住後續所有寫入。

### 5. HTTP API 路由

| 方法 | 路徑 | 功能 | 拒絕條件 |
|------|------|------|----------|
| GET | `/` | 回傳前端頁面 | — |
| GET | `/api/location` | 取得目前座標 | — |
| POST | `/api/location` | 設定單點座標並注入裝置 | 缺少 lat 或 lng → 400 |
| POST | `/api/stop` | 停止行走並清除模擬定位 | — |
| POST | `/api/walk/start` | 依路線開始自動行走 | 路線少於兩點、座標非數值或超出經緯度範圍、速度非數值或不大於零 → 400 |
| POST | `/api/walk/stop` | 停止自動行走 | — |
| GET | `/api/walk/status` | 查詢行走進度與裝置寫入結果 | — |
| GET | `/api/diagnostics` | 逐階段探測裝置連線鏈 | 無——階段失敗仍回 200 |

走路開始端點的驗證由 `_parse_walk_request` 在**啟動工作執行緒之前**完成，而且排在停止前一輪走路之前——被拒絕的請求不會動到任何走路狀態，包含不會把正在進行的移動停下來。驗證失敗時回應 `{"error": "<原因>"}` 與 400，工作執行緒完全不會被建立。

`/api/walk/status` 的回應欄位：`active`（是否移動中）、`lat` / `lng`（目前插值位置）、`progress`（已抵達的座標索引，0 起算）、`total`（總點數）、`speed_kmh`、`device_ok`（裝置寫入結果三態：`null` 尚未有結果 / `true` 成功 / `false` 失敗）、`device_error`（失敗原因，非失敗時為空字串）。

核心的設定座標路由：

`set_location()` 的行為：缺少 `lat` 或 `lng` 時回 400；否則在 `lock` 內把兩者強制轉為浮點數、更新 `current_location`，再經 `_run_async` 呼叫 `_set_location` 寫入裝置。

**設計亮點**：即使沒有連上裝置，API 仍成功回應（`device: False`），讓前端能在純網頁預覽模式下運作。

### 6. 自動沿路行走引擎

後端最複雜的部分。**本節涵蓋兩條自動移動路徑**：單點沿路移動（座標來自路線規劃服務）與多座標依序移動（座標來自使用者輸入）。兩者共用同一個走路端點與同一套引擎，後端以固定節奏沿線插值移動，並把每個位置寫入裝置。

**距離計算（Haversine 公式）** —— 這段不隨功能演進而改變，因此原樣保留：

```python
def _haversine(lat1, lng1, lat2, lng2):
    R = 6371000  # 地球半徑（公尺）
    ...
    return R * 2 * math.atan2(math.sqrt(a), math.sqrt(1 - a))
```

**職責分工**

移動的行為由四個函式協作。這裡只說明各自負責什麼與彼此如何分工；實作細節請看 `app.py`，那裡每一段都有說明「為什麼這樣寫」的註解。

| 函式 | 負責 |
|------|------|
| `_walk_worker(route_coords, speed_kmh, generation)` | 背景執行緒的主體。進入迴圈前先派送**起點寫入**；迴圈中每 200ms 依速度算出應前進的公尺數，沿路線消耗距離（吃完一整段就前進到下一點，否則線性插值），更新 `_walk_state` 並派送一次寫入；迴圈結束後，若是自然走完且路線終點尚未送達，派送**終點補寫**。無論正常走完、被停止或迴圈本身拋錯，收尾都會把移動中旗標歸零。 |
| `_dispatch_walk_write(lat, lng, generation, respect_inflight)` | 派送單次裝置寫入。`respect_inflight` 為真時套用「前一次尚未完成就丟棄本次」的規則（移動期間每個週期的行為）；起點與終點以假值呼叫，是這條規則僅有的兩個具名例外。 |
| `_on_walk_write_done(...)` | 寫入完成回呼。先比對代次，不符表示這筆結果屬於已被取代的那一輪走路，整筆丟棄；相符才記錄成功或失敗到 `_walk_state`，並更新 `_walk_last_sent`。無論是否丟棄都會取出例外，不讓它被 Future 吞掉。 |
| `_parse_walk_request(data)` | 在啟動工作執行緒**之前**把路線每一組座標轉為數值、檢查經緯度範圍，把速度轉為數值並檢查為正。任一項不成立就以 4xx 拒絕。 |

**關鍵機制**

- **速度換算**：`speed_kmh` 換算成每個 200ms 週期前進的公尺數。18 km/h 即每週期 1 公尺。
- **線性插值**：兩個路線點之間平滑移動，不會瞬間跳點；抵達中途點不停頓。
- **起點與終點必定送達**：迴圈的不變式是「先前進、再視情況寫入」，這在路線中段成立，在兩個端點都不成立——起點不該先前進（否則裝置永遠沒到過路線起點），終點之後沒有下一個週期可補救（抵達終點那刻若正好有寫入未完成，本次會被丟棄）。兩者因此各有一次不受丟棄限制的派送。
- **重疊寫入丟棄而非排隊**：較新的座標已包含較舊座標的資訊，排隊只會讓裝置位置愈落愈後。丟棄不計為失敗、不回報為錯誤。
- **代次辨識**：停止走路只等待工作執行緒結束，不等也不取消已派送的寫入協程。上一輪的結果若在新一輪開始後才回來，代次比對會把它丟掉，不污染新一輪的狀態。
- **`threading.Event` 停止旗標**：`_walk_stop_event.wait()` 兼具「補眠」與「可即時中斷」兩用途；它也是「自然走完」與「使用者停止」的判別依據——後者不補寫終點。
- **狀態共享**：`_walk_state` 由前端每 500ms 輪詢 `/api/walk/status` 讀取。

### 7. 連線診斷

`/api/diagnostics` 是唯讀端點，把裝置連線鏈拆成四個依序探測的階段。負責的函式各有分工：

| 函式 / 常數 | 職責 |
|-------------|------|
| `_query_tunneld` | 以標準程式庫的 `urllib` 向 tunneld 的 HTTP 端點取得通道清單。位址取自函式庫公開的 `TUNNELD_DEFAULT_ADDRESS`，不呼叫其底線開頭的私有函式——那是未公開介面，函式庫升版即可能無聲失效。 |
| `_parse_tunnel_records` | 把 tunneld 的回應攤平成裝置清單，欄位原樣回報。同一台裝置可能有多筆通道記錄，每筆各自成為一個項目。 |
| `_diag_probe_connection` | 在裝置鎖保護下確認通道與開發者服務可用，並回報是哪一階段失敗。共用定位服務已建立時直接回報沿用，不另開連線。 |
| `_acquire_rsd` | 取得一條已連線的 RSD 通道。從 `_connect` 拆出來，是為了讓診斷能分辨「通道連不上」與「開發者服務開不起來」——這兩種失敗要做的事不同。 |
| `_open_developer_service` | 在既有通道上開啟 Instruments 通訊與定位模擬服務。 |
| `_diag_stage` / `_diag_build` | 組出階段結果。`_diag_build` 依固定順序輸出四筆，未填入的階段標為未執行。 |
| `_DIAG_STAGE_META` | 四個階段的順序、顯示名稱與失敗時的後續動作。四筆後續動作文字互不相同。 |
| `_default_route_address` | 開一個 UDP socket 並指定外部目標，讓作業系統挑出對外介面後讀回本端位址。UDP 的 connect 不送出封包，因此沒有網路副作用。 |

階段結果採三態：`_DIAG_OK`、`_DIAG_FAILED`、`_DIAG_NOT_RUN`。第三態表示前置階段已失敗、
這一階段根本沒有執行，與「執行後失敗」必須分開——兩者要處理的位置不同。

**設計亮點**：整個端點不寫入座標、不清除模擬定位、不關閉既有連線，也不動走路狀態。
涉及實際連線的兩個階段沿用共用連線而非另開一條，因此不引入任何新的並行狀況；
連線是在序列化定位寫入的同一把 `_device_lock` 下建立的。

## 二、前端 `templates/index.html`

單頁應用，使用 Leaflet 地圖 + nipplejs 搖桿，透過原生 `fetch` 與後端溝通。

### 1. 地圖與標記初始化

地圖以 `L.map` 建立並套用 OpenStreetMap 圖磚，標記以 `L.marker` 建立且設為可拖曳。

- **紅色標記**：目前模擬位置，可拖曳；拖曳結束後更新座標讀數。
- **綠色目的地標記**：點擊地圖放置，作為單點沿路移動的終點；可拖曳調整。

**函式庫可用性守衛**

初始化不是無條件的裸呼叫。建立地圖之前會檢查地圖函式庫的全域物件是否存在、建立過程是否拋錯；任一條件不成立就由 `showMapUnavailable()` 在地圖區域顯示訊息，指出地圖、標記與移動功能不可用，並跳過其後所有地圖相依的初始化。

地圖物件與標記物件被其後數十處引用，沒有可退而求其次的替代路徑——所以這裡不做假降級，而是說清楚哪些功能不可用。地圖不可用時：

| 仍然可用 | 停用或不可用 |
|----------|--------------|
| 座標讀數、兩個速度標籤 | 設定 GPS 位置、置中標記、開始移動、停止移動、沿路走到這裡（五個控制項被設為停用） |
| 搜尋框 Enter 送出查詢、列出結果、點擊外部關閉結果 | 地圖、標記、搖桿移動、路線繪製 |
| 選取搜尋結果會更新座標讀數（跳過標記與地圖視野） | — |

**停用相依控制項**的判準是「按下去會不會用到 `map` 或 `marker`」，是一份可列舉窮盡的清單。停用的按鈕不觸發 click，因此不會送出任何請求，也不會產生執行期例外。

### 2. 搖桿即時移動

`moveByJoystick()` 每 100ms 執行一次：把搖桿向量乘上速度換算成經緯度位移，其中經度的公尺換算會依目前緯度以 `cos` 校正（避免高緯度失真），接著移動標記、讓地圖跟隨、更新座標讀數，並呼叫 `sendLocation()` 邊移動邊傳送。

每 100ms 依搖桿向量與速度計算位移；經度換算會依緯度以 `cos` 校正，避免高緯度失真。地圖跟隨刻意**不帶動畫**——更新頻率本來就是每 100ms 一次，帶動畫的平移會在前一次動畫結束前被新的取代，動畫狀態持續堆疊，表現就是搖桿黏滯、放開後標記還在飄。

**函式庫可用性守衛**

搖桿的可用性檢查與 `showJoystickUnavailable()` 提示**排在地圖初始化之前**，而且整段只用 `typeof` 判斷、不取用地圖函式庫的任何物件。若排在地圖初始化之後，地圖函式庫載入失敗會讓這段守衛連同它要顯示的提示一起不執行，使用者只剩一個沒有任何說明的空白角落。

搖桿的移動是對地圖與標記物件下手，因此**搖桿可用與否同時取決於兩個函式庫**：

| 地圖函式庫 | 搖桿函式庫 | 地圖區域 | 搖桿容器 |
|-----------|-----------|----------|----------|
| 載入 | 載入 | 可互動地圖 | 可運作的搖桿 |
| 載入 | 失敗 | 可互動地圖 | 「搖桿不可用」 |
| 失敗 | 載入 | 「地圖不可用」 | 「搖桿不可用」 |
| 失敗 | 失敗 | 「地圖不可用」 | 「搖桿不可用」 |

**手勢傳播阻擋**

搖桿容器與控制面板都是浮在地圖之上的**兄弟節點**，不是地圖的子元素，因此地圖的手勢處理器仍會收到落在它們範圍內的事件。兩者各以 `L.DomEvent.disableClickPropagation` 與 `disableScrollPropagation` 阻擋傳播——用 Leaflet 自己的工具函式才能涵蓋它內部監聽的完整事件集合。阻擋範圍套用在整個面板上，所以在座標輸入區裡拖曳選字不會平移地圖，在面板內滾輪捲動也不會縮放地圖。搖桿容器另設 `touch-action: none`，否則搖桿上的拖曳會同時被解讀為頁面捲動或地圖手勢。

這段阻擋屬於地圖相依的初始化，因此留在地圖建立成功的分支內。

### 3. 地點搜尋

使用 OpenStreetMap 的 Nominatim 服務查詢地名，回傳最多五筆結果。

**結果的渲染方式**：顯示名稱來自第三方服務，因此**不以字串拼接產生標記**。`makeResultItem(label, lat, lng)` 建立一個元素，把名稱寫進 `textContent`、座標放進資料屬性；名稱裡若含有角括號，會原樣顯示為文字而不被解讀為標記。

**點擊以委派處理**：結果列表上掛一個委派處理器，從被點中的項目的資料屬性讀出座標再交給 `selectResult()`，不再把座標拼進行內事件屬性。這個處理器與搜尋框的 Enter 鍵綁定同樣放在**只依賴 DOM 的初始化**區塊，因此第三方函式庫失效時搜尋與選取仍然可用。

`selectResult()` 更新記憶體中的座標與座標讀數；地圖可用時才移動標記與地圖視野，不可用時跳過這兩步。

### 4. 座標傳送（節流機制）

避免大量請求塞爆後端，採「同時只保留一個在途請求」的節流策略：

```javascript
var sendingLocation = false, pendingLocation = null;

function sendLocation(lat, lng) {
    pendingLocation = { lat, lng };          // 永遠只保留最新一筆
    if (!sendingLocation) _flushLocation();
}

async function _flushLocation() {
    if (!pendingLocation || sendingLocation) return;
    sendingLocation = true;
    var loc = pendingLocation; pendingLocation = null;
    await fetch('/api/location', { method: 'POST', body: JSON.stringify(loc) });
    sendingLocation = false;
    if (pendingLocation) _flushLocation();   // 期間有新座標就再送一次
}
```

**設計亮點**：只保留最新一筆待送座標，請求完成後若有新座標才續送——既不塞車，也不遺漏最終位置。

### 5. 自動沿路行走

**流程**：`walkToMarker()` 向 OSRM 取得起點到綠色目的地的道路座標（回傳是 `[lng, lat]`，需翻轉成 `[lat, lng]`）→ 在地圖畫出路線 → POST 給 `/api/walk/start` → 呼叫 `startWalkPolling()`。實際的座標寫入完全由後端負責，前端只做顯示。

**輪詢**：`startWalkPolling()` 每 500ms 讀一次 `/api/walk/status`，做三件事。

1. **跟隨位置**：移動中時把標記移到後端回報的座標並讓地圖跟隨。
2. **呈現裝置寫入結果三態**（`updateDeviceWarning()`）：

| `device_ok` | 底部狀態列 | 狀態圓點 | 裝置警示區 |
|-------------|------------|----------|------------|
| `null`（尚未有結果） | 等待裝置回應… | 不點亮 | 空白 |
| `true`（成功） | 裝置已連接 | 點亮 | 空白 |
| `false`（失敗） | 裝置寫入失敗 | 不點亮 | ⚠ 加上 `device_error` 的原因 |

只有讀到**明確的成功**才點亮。走路剛開始時第一次寫入的結果還沒回來，若把「不是失敗」當成成功，前端第一次輪詢就會在毫無根據下宣稱裝置已連接。

3. **收尾分流**：讀到走路已結束時，先用最後一次讀到的狀態決定進度顯示，再交給 `stopAutoWalk()` 清理路線。

| 收尾方式 | 觸發 | 進度顯示 |
|----------|------|----------|
| 自然走完 | 輪詢讀到 `active` 為否，且此時仍在多座標移動中 | 保留「第 M 點／共 M 點」 |
| 使用者按停止 | 停止按鈕直接呼叫 `stopAutoWalk()`，不帶保留參數 | 清除 |

移動中的標記位置是伺服器端的**純數學插值**，與裝置寫入成敗無關——沒有第 2 點的呈現，裝置早已凍結時介面仍會顯示一切正常。

### 6. 統一控制面板

除了搖桿以外，所有浮在地圖上的控制項都收在左側的單一面板裡，依實際使用流程分為四個區段：**位置**（設定 GPS 位置、置中標記）、**速度**（自動移動、搖桿兩支滑桿）、**多座標依序移動**（座標輸入、開始移動、錯誤訊息、進度、裝置警示）、**單點沿路**（沿路走到這裡、停止移動）。

- **收起與展開**：`togglePanel()` 切換面板的 `collapsed` 類別，標頭保持可見。收起用 `display: none` 隱藏內容，**元件仍留在文件中**——腳本在啟動時要讀速度控制項推導標籤，移動輪詢也會持續寫入進度與裝置警示；若收起等於從文件移除，這些取用會取到空值並在執行期拋錯。收合狀態刻意不持久化，重新載入回到展開。
- **裝置寫入失敗在收起時仍看得見**：警示同時寫進底部狀態列，而狀態列在面板之外。
- **內部捲動**：面板高度以視窗可用區為上限，超出時由內容區自行捲動，不溢出畫面也不裁切區段。
- **刻意不使用 form 元素**：送出全走非同步請求，`form` 只會帶來按 Enter 觸發提交而清空座標清單的風險。

### 7. 多座標依序移動

使用者在面板中逐行輸入「緯度, 經度」，走一條由這些點串成的折線。**不經過任何路線規劃服務，也不吸附道路**——落點就是輸入的座標。

- **座標清單解析**：`parseCoordInput(text)` 逐行解析，忽略空白行與行首行尾空白。任何一行不是兩個以逗號分隔的數值、或緯度超出 -90～90、經度超出 -180～180，就整批拒絕並回報**輸入的實際行號**（含空白行計數），使用者才對得上自己貼進去的內容。少於兩個座標時回報「至少需要兩個座標」。
- **路線繪製**：`drawMultiRoute(coords)` 為每個座標放一個**編號標記**（1、2、3…依輸入順序），以虛線折線連接，並讓地圖視野涵蓋所有座標。繪製在送出請求之前完成。
- **進度顯示**：輪詢讀到的 `progress` 是已抵達的座標索引（0 起算），顯示為「第 N 點／共 M 點」，後面接上剩餘時間（見第 9 節）。
- **兩種收尾的差異**：

| 收尾方式 | 進度顯示 | 編號標記與折線 | 裝置的最終位置 |
|----------|----------|----------------|----------------|
| 自然走完 | 保留在「第 M 點／共 M 點」 | 移除 | 路線的最後一個座標（必要時由終點補寫送達） |
| 使用者按停止 | 清除 | 移除 | 按下當時已送達的位置，不補寫終點 |

終點狀態存在的時間短於 500ms 的輪詢週期，所以自然走完時是由輪詢在清理路線**之前**先把進度補上並保留——否則使用者幾乎永遠看不到終點那一格。

### 8. 連線診斷面板與窄視窗版面

診斷面板是控制面板的第五個區段。負責的函式：

| 函式 / 常數 | 職責 |
|-------------|------|
| `runDiagnostics` | 向 `/api/diagnostics` 取結果，期間停用按鈕；連不到本機伺服器時分開呈現，避免讀成裝置的問題。 |
| `renderDiagnostics` | 逐階段建立節點呈現名稱、結果、細節與失敗階段的後續動作，並附上伺服器位址與裝置清單。 |
| `DIAG_MARK` / `DIAG_CLASS` | 三態到符號與樣式類別的對應。鍵值與後端的三個結果字串一致。 |

細節與後續動作以 `textContent` 逐段填入，不拼接標記字串——這些文字帶的是裝置與函式庫
回報的例外訊息，內容不由前端決定。

診斷的事件繫結刻意排在「只依賴 DOM 的初始化」區塊，位於任何第三方函式庫初始化之前：
函式庫載入失敗正是最需要診斷的時機之一，那時它必須還能按。

**窄視窗版面**以視窗寬度 768 CSS 像素為斷點，全部由樣式表的條件式規則表達，
不為兩種寬度提供不同標記。窄視窗下控制面板改為貼齊底部、橫向佔滿的抽屜，載入時預設收起
（判斷用 `matchMedia`，與樣式表同一個條件，避免兩處各寫一個門檻）；搖桿縮小並上移，
面板展開時再往上讓一段，靠的是標記順序上搖桿在面板之後，因此可用通用兄弟選擇器選取。
觸控目標在窄視窗一律不小於 44 CSS 像素。

### 9. 走完所需時間

走路是**固定速度的純插值**，不繞路也不重新規劃，所以「還要走多久」是剩餘距離除以速度的
算術結果，不是需要猜測的估計值。整套計算都在前端，後端與 `/api/walk/status` 的回應欄位
未因此增減——狀態查詢本來就回傳位置、已抵達索引與這一輪採用的速度，前端手上也有自己送出
去的路線陣列，輸入早已齊備。

| 函式 | 職責 |
|------|------|
| `haversineMeters` | 後端 `_haversine` 的前端對應，地球半徑與公式一致。 |
| `routeLengthMeters` | 相鄰座標的直線距離總和，即整條路線的長度。 |
| `remainingMeters` | 目前位置到下一個未抵達座標的距離，加上其後每一段線段。 |
| `formatDistance` / `formatDuration` | 依量級選格式的顯示字串。 |
| `updateRoutePreview` | 開始移動前的全長與時間預覽，寫入既有的進度顯示元素。 |

**兩個時機**：

| 時機 | 顯示 | 速度來源 |
|------|------|----------|
| 多座標尚未開始 | 全長 5.7 公里 · 約 18 分 55 秒 | 速度滑桿的當下值 |
| 多座標移動中 | 第 2 點／共 3 點 · 剩餘 12 分 58 秒 | 走路狀態的 `speed_kmh` |
| 單點沿路移動中 | 剩餘 12 分 58 秒 | 走路狀態的 `speed_kmh` |

移動中的速度**必須取自走路狀態，不能取自滑桿**——速度在 `/api/walk/start` 當下就凍結進
`_walk_state`，之後拖滑桿不影響正在跑的那一輪。用滑桿值會讓畫面上的倒數與裝置實際行為
脫節，而且不會有任何錯誤訊息。同理，`updateRoutePreview` 在走路進行中一律不寫入，否則
使用者移動中拖滑桿就會把倒數蓋成預覽。

單點沿路**沒有開始前的預覽**：路線是按下按鈕之後才向 OSRM 取得、取得後立刻送出走路請求，
中間沒有可以插入預覽的時刻。倒數的第一個值本來就等於整條路線的總時間，資訊沒有少。距離
一律自行以 haversine 累加，不用 OSRM 回應裡現成的 `distance` 與 `duration`——前者是路網
長度、後者是開車時間，而走路器是在回傳的折線點之間直線插值前進的。

顯示用「約」而非精確值：走路迴圈每個週期睡「固定間隔減去本週期已耗用時間」，週期超時無法
補回，機器忙碌時實際耗時會略長於計算值。走完之後保留的文字只有座標索引、不含時間——
「剩餘 0 秒」沒有資訊量。

### 10. 目前連線的裝置

狀態列除了「連上了沒有」，還要答得出「連的是哪一台」。

**身分從哪裡來**：`_open_developer_service()` 在定位模擬服務建立成功後，把 RSD 物件上的
`udid`、`ProductType`、`OSVersion` 抄進 `_device_identity`，`_disconnect()` 時清除。記在這個
函式而不是 `_connect()`，是因為診斷的連線探測直接呼叫它、不經過 `_connect()`，而那條路徑
正是使用者主動建立連線的入口。

刻意**不**在查詢時重讀 tunneld 清單再取第一筆——那是在複製 `_acquire_rsd()` 的挑選規則而不是
讀它的結果。兩者只在清單順序不變時才一致，不一致時沒有任何症狀，要等到定位寫到別支手機
才會發現。

機型代號經 `_model_name()` 查 pymobiledevice3 內建的裝置表轉成可讀名稱（`iPhone14,2` →
`iPhone 13 Pro`），查不到就顯示原代號。**不可使用 RSD 物件的 `name` 屬性**：tunneld 建立
裝置物件時傳進去的是通道記錄的 `interface` 欄位，所以那裡裝的是 `utun4` 這類網路介面名。

**`/api/device`**：唯讀端點，回傳 `identity` 與 `visible` 兩個鍵。它**完全不接觸裝置**——不做
RSD 交握、不開開發者服務、不進 `_device_lock`，**也不查詢 tunneld**，只讀記憶體。
這是它能每 3 秒被呼叫一次的前提；若它會接觸裝置，輪詢就會與定位寫入爭搶同一把鎖。

`identity` 與 `visible` 是兩件不同的事：前者只證明伺服器曾經連上誰，後者才說明那台現在還
在不在。

**可見性只在兩個時刻更新**：連線建立時（能連上就代表剛讀到的通道清單裡有它，這個判斷免費且
當下為真）與執行診斷時（診斷本來就會讀清單）。`/api/device` 本身**不查 tunneld**，只回傳記憶體裡
最後一次已知的值。理由是 tunneld 是獨立的 uvicorn 程序，每收到一次查詢就記一行，而啟動腳本把它
丟在同一個終端機的背景——每三秒查一次只是把噪音搬到另一個我們過濾不到的程序。

代價是失去「手機被實體拔掉、伺服器卻仍握著連線物件」的自動偵測。那一種另有更權威且免費的來源：
**實際的裝置寫入**。通道清單只說通道還在不在，寫入結果說的是真的寫得進去嗎。使用者一動手，第一次
寫入失敗就會在狀態列呈現。至於停止模擬、連線關閉這些情況完全不受影響——那只是身分變 null，是記憶體
的事，狀態列照樣在一個輪詢週期內回到「未連接裝置」。

`visible` 是三態：

| `visible` | 意義 | 狀態列 |
|-----------|------|--------|
| `true` | udid 仍在 tunneld 通道清單中 | 機型名 · iOS 版本 已連接 |
| `false` | tunneld 可達但清單裡沒有它 | 機型名 已離線 |
| `null` | tunneld 查不到，無從判斷 | 機型名 · 無法確認狀態 |

三態而非布林的理由與裝置寫入的 `device_ok` 相同：把 tunneld 掛掉說成裝置離線，是把責任推給
手機，而使用者接下來要做的事完全不同——一個是重新插上手機，一個是重啟 tunneld。tunneld 查
不到時端點仍以成功狀態碼回應，查不到是它的正常輸出，不是它自己壞了。

**`renderDeviceStatus`**：狀態列的唯一寫入者。文字由兩半組成——裝置身分（來自輪詢）與裝置
狀態（來自實際操作）。分成兩半，走路中寫入失敗才能顯示成「iPhone 13 Pro 裝置寫入失敗」，
讓「哪一台」與「發生什麼事」同時在場。操作結果只在失敗與等待中時才設值去蓋過輪詢；成功時
交回輪詢，否則一次成功的寫入會把狀態列凍結在「已連接」，之後拔掉手機也不會變。

**診斷面板的裝置清單**：tunneld 的回應只有 udid、介面名、通道位址、通道埠四個欄位，**沒有機型**
——機型只在 RSD 交握之後才存在。但 `_acquire_rsd()` 呼叫的 `get_tunneld_devices()` 本來就對每一筆
通道記錄各做一次交握，回傳的每個物件都帶著機型代號與 OS 版本，而原本的程式只取第一個、其餘全部
丟棄。`_device_models` 把整份清單的 udid → 機型對應留下來，因此**每一台**列出的裝置都有名字，
而這不需要多做任何一次交握。

`_annotate_device_models()` 在組裝診斷回應時替每一筆記錄補上機型與「是否為使用中的那一條通道」，
機型來源依序是目前連線身分與上述對照。

**機型名與使用中標記的判定依據刻意不同**。機型以 udid 比對：同一支手機的每一筆通道記錄都該顯示它是
什麼機型。使用中則以 **udid 加介面名**比對：同一支手機插著線又在同一個區域網路下時，tunneld 會回報
兩筆 udid 相同、介面名不同的記錄（它同時監看 USB 與網路配對兩種來源），而承載連線的只有其中一條——
光比對 udid 會把兩筆都標成使用中，其中一筆在說謊。

介面名取自連線時選用的通道裝置物件的 `name` 屬性，函式庫把該筆通道記錄的 `interface` 欄位填在那裡。
它只供內部判定，不隨身分對外回報。若記錄的介面名對不上任何一筆記錄（通道被重建、介面編號改變），
則**一筆都不標**：少一個提示只是少一個提示，標錯會讓使用者以為自己在操作另一條通道。這一步與 `_parse_tunnel_records()` 分開：後者的契約是「欄位原樣取自
tunneld」，而機型是衍生資訊，混在一起會讓那份契約說不清楚。

兩者皆查不到時**不填欄位**，而不是填空字串——使用者會照著機型名行動，一個錯的名字比一串 udid 更糟。
對照只在連線嘗試時更新，因此允許過期；從未交握過的裝置就沒有條目。

面板上每一筆呈現為兩行：機型名一行（使用中的那一台加註記，機型未知時整行省略、不留空行），原本的
`udid @ 介面名` 降為次要的等寬小字一行。層次不靠新樣式達成——機型名那行不套用類別，繼承清單容器的
一般字級，與既有的等寬小字自然形成主次。介面名的值形如 `usbmux-<udid>-USB`，所以原本那一行會把同
一個 udid 印兩次，這也是它該降為次要行的原因。

**輪詢的日誌噪音**：3 秒一次的輪詢每小時產生一千多行存取日誌，會把這個專案日誌真正要看的
東西洗掉——`[Walk]` 的進度與裝置寫入失敗，那是判斷裝置還活著的主要線索。`_mute_poll_access_log()`
在伺服器啟動時安裝一個過濾器，把身分查詢的**成功**存取日誌擋掉。

**只擋 2xx**，非 2xx 照常記錄。這是整件事的關鍵：一個每三秒被呼叫的端點若開始回 500，日誌是唯一
會說話的地方；整條路徑一併靜音等於讓這個功能自己的故障變成無聲的。

判斷依據是日誌記錄攜帶的參數而非格式化後的整行字串。Werkzeug 以請求行、狀態碼、大小三個參數記錄，
而非 2xx 的請求行會被包上終端色碼——比對格式化結果會在色碼上絆倒，也會隨日誌格式改版失效。路徑以
切出來的欄位精確比對而非子字串，否則 `/api/devices-foo` 這類路徑會一起被吞掉。

刻意**不**改用「沒連線時退避到較長間隔」的做法：那是治標。退到 10 秒每小時仍有數百行，而真正連上
裝置後又回到 3 秒，日誌照樣被洗。問題不在頻率，在於健康檢查不該進存取日誌。`[Walk]` 的輸出走的是
`print`、不經過這個 logger，因此完全不受影響。

**「連線並診斷」**：這顆按鈕在共用連線尚未建立時，會走與正常連線相同的兩個步驟並保留結果
連線，本來就是一顆主動連線鍵。先前叫「執行診斷」，使用者因此不知道畫面上已經能主動連線。
沒有另外新增連線端點——那會是連線探測之上的第二層薄殼，藏不住任何行為，而且失敗時沒有階段
資訊可講，使用者仍得再按診斷。tunneld 本身則無法從畫面啟動：它由啟動腳本以 sudo 執行，而
伺服器是它的非 sudo 子程序。

## 三、圖示產生 `tools/make_icons.py`

產生 iOS 主畫面與資訊清單所需的兩個 PNG 圖示（180 與 512 像素），只用標準程式庫的
`zlib` 與 `struct` 手寫檔案格式。

| 函式 | 職責 |
|------|------|
| `_chunk` | 組出一個 PNG 區塊：長度、標記、資料、CRC。 |
| `_pixels` | 畫出圓角矩形底色與中央的定位標記圖案，回傳未壓縮的 RGBA 掃描列。 |
| `write_png` | 串起 PNG 簽章、`IHDR`、壓縮後的 `IDAT` 與 `IEND`，寫出檔案。 |

之所以不引入 Pillow：iOS 主畫面圖示只接受 PNG（不能改用向量），而為兩個純色圖示
加一個影像處理套件並不成比例。指令稿可重複執行，每次覆寫輸出且結果穩定。
